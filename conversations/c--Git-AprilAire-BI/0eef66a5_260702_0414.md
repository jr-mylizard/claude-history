- The data load finished before the DBT run started, or

## Why my "lock" framing may be wrong for Fabric

Microsoft Fabric's Lakehouse uses **Delta Lake on OneLake**, not a traditional RDBMS. The SQL Analytics Endpoint doesn't use row-level locks the way SQL Server or Snowflake do. So "lock contention" in the classical sense probably isn't what happened.

What's more likely in Fabric is **capacity throttling**. Fabric runs on shared Capacity Units (CUs), and if another workload (a Pipeline, Dataflow Gen2, Spark notebook, etc.) was consuming a large portion of your capacity during that window, the SQL endpoint queries from DBT would get queued or severely throttled — which would explain exactly this pattern: multiple queries hanging for the same duration then all completing together when the competing workload finished.

## How to confirm in Fabric

**1. Fabric Capacity Metrics app** (most useful)
Go to your Fabric capacity in the Admin portal and open the **Microsoft Fabric Capacity Metrics** app. Look at the CU consumption graph for the `23:54 → 01:26` window on July 1–2. If you see a spike from another workload (a pipeline, dataflow, or Spark job) consuming the capacity during that window, that's your cause.

**2. Fabric Monitoring Hub**
In your Fabric workspace, go to **Monitoring Hub** and filter by that time window. You'll see all pipeline runs, dataflow runs, and notebook runs. Look for anything that was running concurrently with your DBT job.

**3. SQL Analytics Endpoint activity**
You can query the SQL endpoint's own activity DMV in real time, but for historical data, the Capacity Metrics app is the right place to look.

The key question to answer: **what else was running in your Fabric workspace between 23:54 and 01:26?** That's what the Monitoring Hub will tell you.

**Claude**

Found the problem. It's in the polling loop in [pipeline_build_dbt.yml](pipeline_build_dbt.yml). Two issues:

**Issue 1: No sleep in the polling loop**
```powershell
Do
{
    $response = Invoke-RestMethod "...runs/$run_id/" -Method 'GET' -Headers $headers
    $statusNum = $response.data.status
    $status = $response.data.status_humanized
} While ($statusNum –lt 4)
```
This hammers the DBT API thousands of times per minute with no delay, which likely triggers rate limiting — causing the API to return empty or malformed responses.

**Issue 2: When the API returns a bad response, `$statusNum` becomes `$null`**
In PowerShell, `$null -lt 4` evaluates to `$true`. So if rate limiting causes even one bad response, `$statusNum` becomes null and the loop **never exits** — regardless of whether DBT finished.

This explains exactly what you're seeing: DBT completes in 22 minutes, but the script keeps looping on null responses until Azure DevOps kills it at 60 minutes.

**Also check:** the `–lt` on line 72 — depending on how that was typed, it may be an **en dash** (–) rather than a hyphen (-). PowerShell's operator is `-lt`. If it's an en dash, the condition is unparseable and may always evaluate to true.

**The fix:**

```powershell
Do
{
    Start-Sleep -Seconds 15
    $response = Invoke-RestMethod "https://ha564.us1.dbt.com/api/v2/accounts/70403103943336/runs/$run_id/" -Method 'GET' -Headers $headers
    $statusNum = $response.data.status
    $status = $response.data.status_humanized
    Write-Host "DBT status: $statusNum - $status"
} While ($statusNum -lt 4)
```

Adding `Write-Host` will also give you visible logs in Azure DevOps each poll cycle, so you can see what's happening instead of guessing.

**One more thing:** line 64 has a hardcoded API key directly in the YAML file. That key is now in your git history and should be rotated and moved to a pipeline variable like `$(APIKey)` on line 58.
