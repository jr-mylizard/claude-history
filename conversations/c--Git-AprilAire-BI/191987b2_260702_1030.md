# Architecture & Test Review — MyLizard

**TL;DR:** The architecture is coherent and pragmatic for a solo-built MDM product, and the iOS enrollment redesign (staged → pre → post) is genuinely good. The three biggest risks are: (1) **contract drift** — `ios.md`, the generated DB types, and the iOS test all describe a system that no longer exists, and the broken test is a direct casualty of that; (2) **the security posture is wider open than "no auth yet" implies** — permissive anon RLS on every table plus `verify_jwt = false` on all 22 edge functions means anyone with the browser-visible anon key can read/write your entire database; (3) **almost none of your tests can run automatically** — only the 5 SQL tests run in CI; everything else needs secrets, a live dev DB, and a physical device.

---

## Architecture: what you have

**MyLizard-Supabase** (the backend): Deno edge functions + Postgres 17. Vendor adapters in `_shared/apis/` (Hexnode for Android, Mosyle for iOS, Cleanbrowsing, SearchAPI), declarative schemas in numbered folders, a trigger-heavy DB (acknowledged legacy pattern — the new iOS code mostly avoids it, which is the right direction).

**MyLizard_NodeJS** (the web): Next.js 16 App Router storefront plus internal tools. It holds no privileged keys — it reads via the anon key and calls edge functions over HTTP. That separation is clean.

**The iOS flow as it exists today** (not as `ios.md` describes it):
1. [stage-device](c:/Git/MyLizard-Supabase/supabase/functions/stage-device/index.ts) — Mac enrollment script captures UDID/serial/apps from the connected iPhone, writes `staged_device_enrollments`, opens the registration form.
2. [pre-enrollment-ios.ts](c:/Git/MyLizard-Supabase/supabase/functions/pre-enrollment-device-setup/pre-enrollment-ios.ts) — form submission upserts customer + `customer_devices` placeholder (`mosyle_device_id` NULL), seeds apps/schedules/DNS categories; supports both the Mac path and a web path that resolves app names from screenshots via SearchAPI.
3. [post-enrollment-ios.ts](c:/Git/MyLizard-Supabase/supabase/functions/post-enrollment-device-setup/post-enrollment-ios.ts) — a pg_cron sweep that polls Mosyle for pending devices and completes enrollment; also serves as the email-sending callback for the profile workflow.
4. Ongoing sync via `sync-apps-and-websites` (`os: "ios"`) → `_shared/util/sync-mosyle.ts` (CDA assign/revoke), with the Install App profile driven by a **Playwright bot in GitHub Actions** because Mosyle has no profile API.

## Architecture findings, in priority order

**1. Documentation and generated types have drifted badly from the code.**
- `ios.md` — which `CLAUDE.md` explicitly tells every agent to read as the source of truth — still describes `set-up-ios-device` and `sync-mosyle` edge functions (deleted), the `ios_devices`/`ios_schedules` tables (merged into `customer_devices`/`device_schedules`), and the old single-file test path. Anyone (human or AI) working from it will build against a dead architecture.
- `db-types.ts` is stale: `staged_device_enrollments` and `dns_device_categories` are missing, forcing `@ts-ignore` in production code ([pre-enrollment-ios.ts:59](c:/Git/MyLizard-Supabase/supabase/functions/pre-enrollment-device-setup/pre-enrollment-ios.ts#L59), [:448](c:/Git/MyLizard-Supabase/supabase/functions/pre-enrollment-device-setup/pre-enrollment-ios.ts#L448)) and an `as unknown as` cast in the test. Running `bin/gen-db-types.sh` and deleting those suppressions is cheap and restores your own "never use `any`" guarantee.
- This same drift is what broke the iOS test (below). I'd treat "update ios.md + regen types" as one work item and do it before Android registration starts, since that work will copy these patterns.

**2. Security: the exposure is broader than "Auth isn't set up yet."** Migration `20260527000002` grants `anon` full read/write on **every** public table, and all 22 edge functions are `verify_jwt = false`. Since the anon key ships to every browser, anyone can dump `customers` (names, emails, phones, addresses) or rewrite `device_schedules` on a child's device from the console today. Auth-as-login can wait; I'd still do two cheap things now: (a) a shared-secret header or Vercel-level protection on the internal pages *and* the sensitive edge functions (`pre-enrollment-device-setup`, `delete-device`, `hexnode-update-apps-in-app-group`), and (b) replace the blanket `anon_all` policies with read-only policies on the handful of tables the storefront actually reads (`vw_stripe_products` sources, `email_subscribers` insert-only). That shrinks the blast radius without building the portal.

**3. The Mosyle Playwright workflow is your most fragile link.** [triggerMosyleProfileWorkflow.ts](c:/Git/MyLizard-Supabase/supabase/functions/_shared/util/triggerMosyleProfileWorkflow.ts) is fire-and-forget: if the GitHub dispatch fails, the runner flakes, or Mosyle changes its UI, the device profile silently never updates and the customer email never sends. You've already added post-save verification inside the workflow (good), but nothing watches for the workflow *not running*. A small pg_cron reconciliation — alert when `ios_device_apps` rows sit with pending `mosyle_status` beyond N minutes — would convert silent failures into emails.

**4. Cross-repo contract coupling is informal.** The web repo hand-rolls `fetch(`${supabaseUrl}/functions/v1/...`)` calls in four places with duplicated header logic, and the request/response types live only in the Supabase repo (`edge-function-types.ts`). The iOS test broke for exactly this reason: a producer changed its contract and consumers found out at runtime. Even a lightweight step helps — a shared types package, or copying `edge-function-types.ts` into the web repo with a "regenerate from" header comment, plus one `invokeEdgeFn`-style helper in `src/lib`.

**5. Small hygiene items:** `_shared/email-templates/` and `_shared/email_templates/` both exist (pick one); internal routes are inconsistent (`app/(internal)/internal/user-registration-ios` vs `app/internal/device_management` — the latter bypasses the route-group layout); `jr@mylizard.net` is hardcoded as the ops recipient in multiple functions (an `INTERNAL_ALERT_EMAIL` env var would help when this stops being just you); `testing.js` and `tmp.txt` sit at the Supabase repo root.

## Test review

**Inventory:** 8 Android integration tests (one scenario per file — nice structure), 2 iOS tests (`ios.test.ts` end-to-end + `add-apps-errors.test.ts`), 3 "unit" tests, 5 SQL pgTAP tests. The web repo has **zero tests and no test runner**.

**The broken iOS test — diagnosis.** [ios.test.ts](c:/Git/MyLizard-Supabase/supabase/functions/tests/ios/ios.test.ts) type-checks cleanly (I verified with `deno check`); it fails at runtime because **step 1 calls `post-enrollment-device-setup` with the pre-unification contract** (`mosyleDeviceName`, `timezone`, `nickname`, `addToDeviceGroups`) — there's already a TODO at [line 241](c:/Git/MyLizard-Supabase/supabase/functions/tests/ios/ios.test.ts#L241) acknowledging this. The function is now a polling sweep expecting a placeholder row created by *pre*-enrollment. So step 1 gets back a sweep summary (`{enrolledCount, ...}`) instead of a device row, its assertions fail, `runSteps` halts, and every later step (which are still valid tests of add-apps/sync-mosyle) never runs. **The fix is a rewrite of the enrollment portion, not a tweak:**
1. Seed a `staged_device_enrollments` row (via `stage-device` or direct insert) for the test device's IMEI.
2. Call `pre-enrollment-device-setup` with `os: "ios"`, customer fields, and the IMEI; assert the placeholder `customer_devices` row, the "Always" schedule, and DNS categories.
3. Call `post-enrollment-device-setup` and assert `enrolledCount === 1` and that `mosyle_device_id`/`serial` were backfilled (requires the physical test device to actually be in Mosyle, as before).
4. Steps 2–10 (add-apps, schedules, sync, App Store timer) should then work nearly as-is since they already use the unified tables.

**Other iOS-test issues while you're in there:**
- Cleanup only runs when all steps pass, and it matches devices by `nickname` only. A failed run strands rows in `customer_devices`, `ios_apps`, and Mosyle CDAs, and a crash outside a step skips cleanup entirely. Wrap the whole thing in `try/finally` — the "before" cleanup already makes reruns safe, but Mosyle state (CDAs, group membership) leaks between runs.
- The rewrite should also decide what to do about the parts of post-enrollment that are inherently untestable here: the GitHub workflow dispatch and the email paths (`sendEmailForDeviceId`, scoped runs). A `dryRun`/`skipWorkflow` flag in the request body — or an env check — would let the test cover the DB logic without spamming emails or burning Actions runs.
- Untested iOS surface worth adding after the rewrite: the pre-enrollment **web path** (screenshot names → SearchAPI → unresolved-app persistence in step 5b), **re-enrollment** (the `isReEnrollment` branch), and `reset-ios-device`.
- Trivial but real: the "Always"/all-day blocks end at `23:59:59` with an exclusive end, so every device has a one-second nightly window where all schedules are inactive — harmless unless a sync lands in it, but `24:00:00` or documenting the convention would close it.

**Suite-level observations:**
- **Only the SQL tests run in CI** ([database-tests.yml](c:/Git/MyLizard-Supabase/.github/workflows/database-tests.yml) — the Deno test step is a commented-out TODO). Everything else needs `.env` secrets, a served local stack, live Hexnode/Mosyle/Resend, and a physical device. That's a deliberate integration-first philosophy and it does catch real vendor-behavior bugs, but it means regression detection is entirely manual. The highest-leverage improvement isn't more tests — it's carving out a subset that runs on every PR: the Zod-validation/error-path tests (like `add-apps-errors.test.ts`) and any pure logic in `_shared/util` could run against `supabase start` + `functions serve` in Actions with no vendor secrets.
- **The `tests/unit/` naming is misleading** — `post-enrollment-device-setup.test.ts` drives a real Hexnode device (ID 20) end-to-end. Renaming the folder `integration-singles/` or similar costs nothing and prevents someone assuming `deno task test-unit` is safe to run casually.
- `send-email.test.ts` deletes and restores `Deno.env` globals — fine today, flaky the day tests run in parallel.
- **The web repo's zero tests** is acceptable for marketing pages, but `createCheckoutSession` is the money path and `parseAppScreenshots` (Claude-based) feeds enrollment. One vitest suite around the cart→Stripe-session mapping (mixed purchase/rental carts, affiliate rejection) would be the single best test investment in that repo.
- `CLAUDE.md`'s testing section also still points at `tests/ios.test.ts` and describes `resetForTest` as Android-only "clean up manually" for iOS — update alongside `ios.md`.

You're using the word "contracts" in a way I'm not familiar with. What do you mean by it?

---

**Claude**

By "contract" I mean the agreed-upon shape of the data two pieces of code exchange — what one side promises to accept and what it promises to return. For an edge function like `post-enrollment-device-setup`, its contract is: "send me a POST body with these fields (`udid`, `sendEmailForDeviceId`, ...) and I'll respond with JSON shaped like `{enrolledCount, pendingCount, results}`."

It's the same idea as a function signature, just applied across an HTTP boundary. The important difference is that nothing enforces it. When you call a TypeScript function with the wrong arguments, the compiler stops you. But when the iOS test calls `post-enrollment-device-setup` over HTTP with `mosyleDeviceName` and `timezone`, no compiler knows that the function stopped accepting those fields — the request still goes out, the Zod schema on the other end ignores or rejects it, and you only find out at runtime.

That's what I meant by "contract drift": the function changed what it accepts and returns (the contract changed), but its callers — the test, and potentially the web repo — were still written against the old version. The Zod schemas in `edge-function-types.ts` *are* the contracts, written down; the problem is that consumers in other files or other repos don't automatically get updated (or even warned) when a schema changes.

**Claude**

Honest answer: two of the five, and for the same underlying reason — they involve design judgment where mistakes are silent, rather than mechanical work where mistakes are loud.

**#2 (iOS test rewrite) is the strongest candidate.** It's not the typing that's hard — it's the reasoning across four systems at once: what the staged-record seeding should look like, how to handle the polling/timing semantics of the post-enrollment sweep against a real physical device, where to put the test seam for the GitHub workflow dispatch and email paths (a `dryRun` flag is an API design decision that outlives the test), and getting the cleanup semantics right so failed runs don't strand state in Mosyle. A weaker model will produce something that *looks* like a rewritten test but subtly asserts the wrong things or leaks state — and since this test can't run in CI, you won't discover that until a manual run weeks later.

**#3 (RLS narrowing) is the other.** The failure modes are asymmetric and both silent: too strict and some storefront query or the WeWeb site quietly returns empty results; too loose and the PII hole stays open while looking fixed. Doing it properly means exhaustively enumerating every anon-key access path across MyLizard_NodeJS, WeWeb, *and* the edge functions before writing a single policy. That enumeration is exactly the kind of thoroughness that degrades first on smaller models. A reasonable split: use the stronger model to produce the access-path inventory and policy design, then any model can write the SQL.

**#1, #4, and #5 are fine on Sonnet.** The type regen is a script run plus deleting suppressions; the doc updates are summarization of code we've already mapped; the CI workflow is YAML plumbing where failures are immediately visible in the Actions log; the reconciliation cron is a small, well-scoped query + email. All of these are self-verifying — if they're wrong, you find out fast and cheaply.

One caveat: you switched this session to Fable 5 at the start, so you're already on the high end — if you're deciding where to *save* by dropping down, #1/#4/#5 are the safe places to do it.

**You**

If I was having problems with the Playright script and kept getting different errors each time, and different errors when running locally vs. through github, would that make sense to fix on a model higher than sonnet?

---

**Claude**

Yes — and flaky browser automation is arguably a *better* fit for a stronger model than the tasks I listed, but for a specific reason worth understanding, because it also tells you what the model alone won't fix.

**Why it fits:** "Different errors each time" is the signature of nondeterminism — timing races, elements asserted before async UI settles, network variance. The failure mode of weaker models on this class of problem is whack-a-mole: each run produces a new error message, the model patches *that symptom* (add a sleep here, a retry there), and the underlying race just moves. Ten iterations later the script is slower, uglier, and still flaky. Stronger models are meaningfully better at stepping back and saying "these five different errors are one root cause" and at the discipline of instrumenting before fixing. Diagnosis from sparse, noisy evidence is exactly where the capability gap shows up most.

**What no model fixes:** your iteration loop is brutally slow — edit, push, dispatch the workflow, wait minutes, get back one error string. The bottleneck is information per run, not reasoning. So whichever model you use, the first move should be to make each failure self-explaining rather than to attempt fixes:

- Turn on Playwright tracing, video, and screenshots-on-failure, and upload them as workflow artifacts. One trace file replayed in the trace viewer usually tells you more than twenty blind runs.
- Log the environment at startup (browser version, viewport, headless mode, runner IP) in both places, then diff them.

**On the local-vs-GitHub split specifically**, the usual suspects are: headless vs. headed rendering differences, viewport size (elements hidden behind responsive layouts), unpinned browser versions, slower CI CPUs blowing past timeouts, and — particularly relevant for you — Mosyle treating a GitHub datacenter IP differently than your home IP (security challenges, extra verification interstitials, session behavior). That last one produces errors that are *impossible* to reproduce locally, and the only way to see it is a screenshot or trace from the CI run.

So my recommendation: yes, use Opus or Fable for this one, but frame the task as "instrument the script so failures are diagnosable, reproduce the failure with artifacts, identify the root cause, then fix it" — not "fix the errors." That framing prevents the whack-a-mole pattern on any model, and the stronger model is more likely to hold to it when the errors get weird. This connects to my architecture finding #3, too: whatever hardening comes out of the debugging (explicit waits, post-action verification), the reconciliation alert is still worth having, because a UI-scraping bot against a third party's admin panel will never be permanently fixed — Mosyle will eventually change something.
