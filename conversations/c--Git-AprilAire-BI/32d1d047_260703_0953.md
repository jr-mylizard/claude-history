# Step 2 — Proposed replacement design

**Principle (this is the "Vercel handles it" answer):** the browser keeps anon read access to exactly two catalog views and nothing else. Every write and every internal read moves into Next.js **server actions running on Vercel** with the service-role key (a server-only env var — never `NEXT_PUBLIC_`). Your UI components don't change; only their data calls move one layer back. WeWeb is retired rather than accommodated.

### 1. One migration
- Drop `anon_all` **and** `authenticated_all` from all 38 tables (no users exist yet; the portal can add real authenticated policies later).
- Enable RLS on `device_schedules`, `device_schedule_blocks`, `device_category_schedules` (no anon policies).
- `REVOKE SELECT FROM anon` on all views **except** `vw_stripe_products` and `vw_featured_listings` (public catalog data by nature).
- No anon insert policy on `contacts` — the newsletter moves server-side (an insert-only policy can't support your upsert-and-update-consent flow; the review's "email_subscribers" is today's `contacts`).
- Drop the anon `INSERT` storage policy on `device-app-lists` (bucket stays public-read since enrollment emails and edge functions fetch by URL; signed URLs can be phase 2).

### 2. Next.js changes
- New `src/lib/supabase/admin.ts` (service-role client, `import "server-only"`); `SUPABASE_SERVICE_ROLE_KEY` added as a Vercel branch-specific env var (dev branch → dev key, master → prod key — same pattern as your existing setup).
- **DeviceManagement**: its ~25 direct table calls become server actions in one `app/actions/deviceManagement.ts` module; component logic/UI untouched.
- **RegistrationForm**: screenshot upload + `pre-enrollment-device-setup` call become a server action.
- **NewsletterForm**: upsert becomes a server action.
- **Gate `/internal/*`**: Next middleware with HTTP Basic auth against an `INTERNAL_PASSWORD` env var (matcher `/internal/:path*`). Single-user, zero UI to build, upgradeable to Supabase Auth when the portal lands. `/register` stays public (customers use it) — its protection is that the edge function behind it is no longer anonymous (below).

### 3. Edge function gating
- Sensitive functions get an in-function check: `Authorization` bearer must equal `SUPABASE_SERVICE_ROLE_KEY` (already in every function's env — no new secret to mint). Callers: Vercel server actions (env var), pg_cron (vault token — needs confirming it's the service key), GitHub workflow (already has it), Mac app (key goes in its `config.env`, which is already out of git).
- Gated: `pre-enrollment-device-setup`, `post-enrollment-device-setup`, `stage-device`, `add-apps`, `delete-device`, `reset-ios-device`, `hexnode-*`, `sync-apps-and-websites`, `send-broadcast`, `send-campaign-emails`, `send-sms`, `export-sms-contacts`, `sync-resend`, `refresh-debloat-lists`, `stripe-payment-links`, `send-daily-sales-summary`, `send-transactional-email`.

### 4. Rollout order (each step is backward-compatible until the last)
Deploy Next.js changes + env vars → gate edge functions → apply the migration → verify register/device-management/catalog end-to-end.

## 2. The middleware I have in mind

A single `middleware.ts` file in the Next.js repo (Next may call it `proxy.ts` in v16 — I'll check the bundled docs before writing it, per your AGENTS.md). It's code that Vercel runs *before* any matched request reaches a page:

```ts
export const config = { matcher: ["/internal/:path*"] }

export function middleware(req: NextRequest) {
  const auth = req.headers.get("authorization")
  // expects "Basic base64(user:password)" — compared against
  // INTERNAL_USER / INTERNAL_PASSWORD env vars set in Vercel
  if (auth === expectedBasicAuthValue) return NextResponse.next()
  return new NextResponse("Authentication required", {
    status: 401,
    headers: { "WWW-Authenticate": 'Basic realm="MyLizard Internal"' },
  })
}
```

What this means in practice: the first time you open `/internal/device_management`, the **browser itself** pops its native username/password dialog (no login page to build, no session table, no cookies to manage). You enter the credentials once and the browser remembers them for the session. Anyone without the password gets a 401 before the page — or any of its data — ever loads. It protects every current and future `/internal/*` route automatically via the matcher.

Why this over Supabase Auth right now: it's one file plus two env vars, it can't drift out of sync with anything, and it's a placeholder you rip out the day the customer portal brings real authentication (at which point `/internal` becomes a role check on actual users). The real security boundary isn't the middleware anyway — it's that after this work, the pages' data access runs through server actions with the service key, and the anon key can no longer touch those tables at all. ## What the docs say, and what I changed

**The key model** (from Supabase's migration guide, checked via their docs):
- Legacy `anon`/`service_role` JWT keys keep working **until end of 2026** — both generations work simultaneously, so you migrate at your own pace.
- Deployed functions get the new keys in a **different env var**: `SUPABASE_SECRET_KEYS`, a JSON object keyed by key name (`{"default": "sb_secret_..."}`), alongside the legacy `SUPABASE_SERVICE_ROLE_KEY`.
- New keys aren't JWTs, so they must go on the `apikey` header, and functions must use `verify_jwt = false` + authorize in code — which is exactly the architecture we already have. Our approach is the documented pattern.

**Changes made:**
- [require-internal-auth.ts](supabase/functions/_shared/util/require-internal-auth.ts) now builds its allowlist from **both** `SUPABASE_SECRET_KEYS` (all named keys in the dict) and the legacy `SUPABASE_SERVICE_ROLE_KEY`, and checks both the `apikey` header and the `Authorization` bearer. Still fails closed if neither env var exists.
- Node [admin.ts](../MyLizard_NodeJS/src/lib/supabase/admin.ts) sends the key on both headers, so the same env var works whether you put the new `sb_secret_...` or the legacy JWT in it. (The Mac script already sent both headers; pg_cron/EF-triggers send `Authorization` only, which the gate also accepts.)
- CLAUDE.md and `.env.example` updated to say "use an `sb_secret_...` key (preferred); legacy JWT also works."

Leave the existing vault entry's **name** alone, but don't put the Vercel key in it — give each caller its own key. Here's the reasoning:

**The vault isn't where Vercel reads from.** Vercel gets its key from its own env var (`SUPABASE_SERVICE_ROLE_KEY` in the Vercel project settings). The vault's `supabase_bearer_token` serves exactly one audience: SQL inside the database — pg_cron and the EF-trigger helper look it up *by that name*. So there should be exactly one vault row named `supabase_bearer_token`, and adding a second row under another name would do nothing (the SQL only ever queries that name).

**One named key per caller is the whole point of the new key model.** The gate accepts *any* of your secret keys (it validates against the full `SUPABASE_SECRET_KEYS` dictionary), so the clean setup is:

| Secret key name (API Keys page) | Where its value lives | Used by |
|---|---|---|
| `vercel` (the one you just made) | Vercel env var `SUPABASE_SERVICE_ROLE_KEY` | Server actions |
| `database` (create one more) | Vault row `supabase_bearer_token` (**update its value**) | pg_cron + EF triggers |
| `default` | local `supabase/functions/.env`, Mac app `config.env` later | Tests, enrollment app |

You *could* reuse the Vercel key's value in the vault and it would work — but then the day you rotate or revoke the Vercel key, your crons silently start getting 401s too. Separate keys mean you can revoke one consumer without touching the others, which is exactly the capability the new keys added.

So concretely: create one more secret key named something like `database`, then update the existing vault row's value to it:

```sql
select vault.update_secret(
  (select id from vault.secrets where name = 'supabase_bearer_token'),
  'sb_secret_...'   -- the "database" key
);
```

One caution: vaults are per-environment. If the dashboard you're looking at is the **dev branch's** vault, this is the fix that unblocks the gating there. Production's vault needs the same treatment at merge time — with keys created on the production project, since dev-branch keys don't work against prod.

**The database calling "itself" still goes out the front door.** When pg_cron fires `net.http_post` at `sync-apps-and-websites`, that request leaves Postgres, travels over HTTPS to the public functions gateway, and arrives looking exactly like any other internet request. **Claude**

That line in your CLAUDE.md is about the pattern in `50 EF Triggers`: a row changes in Postgres, a trigger fires, and `.ml_call_edge_function` makes an HTTP call out of the database to an edge function — "reactive" plumbing where writing data *is* the API call. The alternatives are all things your codebase already does, because you've been quietly migrating away from this pattern for months:

**1. Reconciliation loops (your main replacement).** Instead of "a row changed, immediately go tell Hexnode/Mosyle," writes just update tables, and a periodic job compares desired state against actual state and fixes the difference. That's exactly what `sync-apps-and-websites` is: `vw_desired_mosyle_cdas_state` says what *should* be true, `allowed_in_mosyle` says what *is* true, and the sync acts on the delta every 3 minutes. Your git history is a trail of exactly this conversion — `cleanbrowsing_cron_driven`, `drop_reactive_sync_chain`, `drop_reactive_hexnode_triggers`, and most recently `drop_post_enrollment_ios_fn` + `poll_ios_enrollment_cron` (iOS enrollment used to be event-driven; now the sweep just polls for pending devices). The big win: a lost event doesn't mean lost work. If the Mosyle call fails, the next tick retries automatically, because the *state* still says "not synced yet."

**2. The caller orchestrates.** Whoever wrote the row is usually already an edge function or server action — a runtime with proper HTTP, secrets, logging, and error handling. So it just does the follow-up work itself instead of bouncing through the database. `add-apps` inserting into `ios_apps` and then calling the iTunes API directly is this; the legacy version was "INSERT into `ios_app_lookups` → trigger → `searchapi-get-ios-app-details`" — which is precisely the remaining `502 Search API` trigger cluster your CLAUDE.md calls legacy.

**3. An outbox/queue, for when you truly need "don't lose this event."** Write an event row in the same transaction as the data change, and let a cron-driven worker drain the table. You get the trigger's transactional guarantee without HTTP inside Postgres. (Supabase now ships pgmq/Queues for exactly this, but a plain table works fine at your scale.)

Why the trigger version is worth avoiding: the control flow is invisible (an `INSERT` has network side effects you can't see at the call site), `pg_net` is fire-and-forget so failures vanish silently with no retry, every environment's triggers fire on every write (local resets, branch DBs), testing a table write suddenly requires the whole functions stack running, and — the thread we just pulled — the database needs its own copy of a privileged credential to do any of it.

The one legitimate holdout is pg_cron itself, which still initiates HTTP on a schedule. Even that has an inversion available: since you're on Vercel, [Vercel Cron](https://vercel.com/docs/cron-jobs) (or a scheduled GitHub Action) could call `sync-apps-and-websites` from *outside*, at which point nothing inside Postgres ever makes an HTTP call again and the vault key ceases to exist. Not urgent — the current cron works — but it's the endpoint of the direction you're already moving.
