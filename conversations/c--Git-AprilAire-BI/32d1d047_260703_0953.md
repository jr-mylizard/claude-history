# Step 2 — Proposed replacement design

**Principle (this is the "Vercel handles it" answer):** the browser keeps anon read access to exactly two catalog views and nothing else. Every write and every internal read moves into Next.js **server actions running on Vercel** with the service-role key (a server-only env var — never `NEXT_PUBLIC_`). Your UI components don't change; only their data calls move one layer back. WeWeb is retired rather than accommodated.

### 1. One migration
- Drop `anon_all` **and** `authenticated_all` from all 38 tables (no users exist yet; the portal can add real authenticated policies later).
- Enable RLS on `device_schedules`, `device_schedule_blocks`, `device_category_schedules` (no anon policies).
- `REVOKE SELECT FROM anon` on all views **except** `vw_stripe_products` and `vw_featured_listings` (public catalog data by nature).
- No anon insert policy on `contacts` — the newsletter moves server-side (an insert-only policy can't support your upsert-and-update-consent flow; the review's "email_subscribers" is today's `contacts`).
- Drop the anon `INSERT` storage policy on `device-app-lists` (bucket stays public-read since enrollment emails and edge functions fetch by URL; signed URLs can be phase 2).

### 2. Next.js changes
- New `src/lib/supabase/admin.ts` (service-role client, `import "server-only"`); `SUPABASE_SERVICE_ROLE_KEY` added as a Vercel branch-specific env var (dev branch → dev key, master → prod key — same pattern as your existing setup).
- **DeviceManagement**: its ~25 direct table calls become server actions in one `app/actions/deviceManagement.ts` module; component logic/UI untouched.
- **RegistrationForm**: screenshot upload + `pre-enrollment-device-setup` call become a server action.
- **NewsletterForm**: upsert becomes a server action.
- **Gate `/internal/*`**: Next middleware with HTTP Basic auth against an `INTERNAL_PASSWORD` env var (matcher `/internal/:path*`). Single-user, zero UI to build, upgradeable to Supabase Auth when the portal lands. `/register` stays public (customers use it) — its protection is that the edge function behind it is no longer anonymous (below).

### 3. Edge function gating
- Sensitive functions get an in-function check: `Authorization` bearer must equal `SUPABASE_SERVICE_ROLE_KEY` (already in every function's env — no new secret to mint). Callers: Vercel server actions (env var), pg_cron (vault token — needs confirming it's the service key), GitHub workflow (already has it), Mac app (key goes in its `config.env`, which is already out of git).

### 4. Rollout order (each step is backward-compatible until the last)
Deploy Next.js changes + env vars → gate edge functions → apply the migration → verify register/device-management/catalog end-to-end.

## 2. The middleware I have in mind

A single `middleware.ts` file in the Next.js repo (Next may call it `proxy.ts` in v16 — I'll check the bundled docs before writing it, per your AGENTS.md). It's code that Vercel runs *before* any matched request reaches a page:

```ts
export const config = { matcher: ["/internal/:path*"] }

export function middleware(req: NextRequest) {
  const auth = req.headers.get("authorization")
  // expects "Basic base64(user:password)" — compared against
  // INTERNAL_USER / INTERNAL_PASSWORD env vars set in Vercel
  if (auth === expectedBasicAuthValue) return NextResponse.next()
  return new NextResponse("Authentication required", {
    status: 401,
    headers: { "WWW-Authenticate": 'Basic realm="MyLizard Internal"' },
  })
}
```

What this means in practice: the first time you open `/internal/device_management`, the **browser itself** pops its native username/password dialog (no login page to build, no session table, no cookies to manage). You enter the credentials once and the browser remembers them for the session. Anyone without the password gets a 401 before the page — or any of its data — ever loads. It protects every current and future `/internal/*` route automatically via the matcher.

Why this over Supabase Auth right now: it's one file plus two env vars, it can't drift out of sync with anything, and it's a placeholder you rip out the day the customer portal brings real authentication (at which point `/internal` becomes a role check on actual users). ## What the docs say, and what I changed

**Claude**

Honestly, "better" oversells it — cron is cron; the scheduling itself is equivalent. The differences are about *where the credential lives, where failures surface, and how the schedule is managed*. And in your specific setup there's a real catch worth knowing before you'd ever switch.

**What Vercel cron (or any external scheduler) genuinely improves:**

- **It completes the credential story we've been discussing.** Nothing inside Postgres holds a key or makes an HTTP call anymore — the vault row, `pg_net`, and `.ml_call_edge_function` all become deletable. The database goes back to being just a database.

**The catch for you specifically:** Vercel cron jobs fire only against the **production deployment** of a project. Your dev branch is a branch deployment — it wouldn't get cron ticks. So "move to Vercel cron" really means "prod uses Vercel cron, and dev needs something else" (a scheduled GitHub Action per branch, or keeping pg_cron on dev anyway). pg_cron's per-Supabase-branch nature — the very thing that makes it annoying to manage — is also what makes it fit your preview-branch workflow. ## Basic-auth middleware: strong precisely because it's dumb

Its security virtue is the near-absence of attack surface. There's no signup endpoint, no password-reset flow to poison, no OAuth redirect to misconfigure, no session store, no token issuance — just a string comparison at the edge before any page code runs. Most auth vulnerabilities live in the *machinery* of auth (reset emails, redirect allowlists, session fixation, JWT parsing), and this approach simply doesn't have that machinery. For a one-operator admin surface, that's a genuinely better security posture than a full auth system configured in an afternoon.

Its weaknesses are the flip side of having no machinery:

- **One shared credential, no identity.** No audit trail of *who* did something (fine while "who" is only you), no per-person revocation, no MFA, no expiry — the credential rides along on every request until you change the env var.
- **No brute-force protection built in.** Nothing locks out repeated guesses; your defense is a long random password (make it one).
- **It only guards the door, not the data.** Everything behind it runs with the service key. The entire security argument is "only someone past the middleware can invoke these server actions." One layer, enforced in application code. A bug in a server action — say, one that takes a `deviceId` parameter — has nothing beneath it to catch a mistake.

## Supabase Auth: the point isn't login, it's RLS

What Supabase Auth actually buys you is that **identity reaches the database**. A logged-in user's requests carry their JWT, and Postgres itself evaluates `auth.uid()` inside RLS policies on every row. That moves authorization from "did the app code remember to filter?" to "the database refuses, structurally." It's defense in depth: an application bug that forgets a `WHERE customer_id = ...` clause leaks nothing, because the policy applies it anyway.

The cost is that you inherit all the machinery: signup and reset flows, email deliverability, redirect URL allowlists, the SSR cookie/session dance, and — most importantly — **your RLS policies become security-critical code**. A wrong policy is a silent data leak. That's a real ongoing responsibility, not a one-time setup.

## Where each belongs on your roadmap

The line to draw is by *audience*, not by replacing one with the other:

- **Customer portal → Supabase Auth + RLS, unambiguously.** Customers must see only their own devices, schedules, and orders — that's precisely the `auth.uid()` shape RLS exists for. And critically: portal pages should query with the **user's session client** (publishable key + their JWT), *not* the service key with app-level filtering. The database does the scoping. Today's migration set this up well, incidentally — `authenticated` currently has no policies, so the portal work is purely *additive*: write per-table policies like "authenticated can select customer_devices where the device belongs to their customer record" and grant nothing more. You even have groundwork already: the `customers_auth_and_fk` migration from May links `customers` to auth users.

- **`/internal` admin → the middleware is fine indefinitely**, and arguably should stay even after the portal exists. Admin operations legitimately need cross-customer access, which means the service key and app-code authorization anyway — Supabase Auth wouldn't add the RLS benefit there unless you build role-based policies, which is a lot of ceremony to protect you from yourself. The natural upgrade path, *if* you ever add a second staff member, is swapping Basic auth for a Supabase Auth login with an `is_admin` check in the proxy — same gate location, real identities behind it.

So the end state looks like three trust tiers, which is exactly what today's work carved out: **anon** = two catalog views and nothing else; **authenticated** = per-user rows via RLS (future portal); **service key** = internal surfaces and machinery, gated by things other than the database. The middleware isn't a stopgap you'll regret — it's the correct tool for the tier it guards.

The obstacle: `ios_device_apps.device_id` has a foreign key to `customer_devices(device_id)` that is neither `ON UPDATE CASCADE` nor `DEFERRABLE`. So `UPDATE customer_devices SET device_id = 'new'` fails immediately — the moment the parent key changes, 14 child rows would be orphaned, and Postgres checks that at the end of the statement. You can't update the children first either (the new parent doesn't exist yet). Hence the three-step shuffle, wrapped in a transaction so no cron tick ever sees a half-renamed device:

```sql
BEGIN;

-- 1. Create the new parent: copy the row under the new device_id.
--    The column list deliberately omits `id` (serial → gets a new one)
--    and `created_at`/`updated_at` (defaults apply).
INSERT INTO customer_devices (
  device_id, customer_id, nickname, operating_system, mdm_vendor,
  imei, serial, model_name, os_version, timezone, enabled,
  mosyle_device_id, mdm_vendor_id, mosyle_install_profile_name,
  install_profile_dispatch_attempts, install_profile_last_dispatched_at,
  app_store_enabled, app_store_should_be_enabled_until
)
SELECT
  'WI_608A_JR_001_P_001', customer_id, nickname, operating_system, mdm_vendor,
  imei, serial, model_name, os_version, timezone, enabled,
  mosyle_device_id, mdm_vendor_id, mosyle_install_profile_name,
  install_profile_dispatch_attempts, install_profile_last_dispatched_at,
  app_store_enabled, app_store_should_be_enabled_until
FROM customer_devices WHERE device_id = '00008110-000A40A201EBA01E';

-- 2. Repoint the children. ios_device_apps is legal now because the new
--    parent exists. The other two are plain varchar columns with no FK
--    (device_schedules/dns_device_categories are shared with Android,
--    which uses a different id type — so no constraint was ever declared).
UPDATE ios_device_apps       SET device_id = 'WI_608A_JR_001_P_001' WHERE device_id = '00008110-000A40A201EBA01E';
UPDATE device_schedules      SET device_id = 'WI_608A_JR_001_P_001' WHERE device_id = '00008110-000A40A201EBA01E';
UPDATE dns_device_categories SET device_id = 'WI_608A_JR_001_P_001' WHERE device_id = '00008110-000A40A201EBA01E';

-- 3. Delete the old parent — safe now; its ON DELETE CASCADE has no
--    children left to take with it.
DELETE FROM customer_devices WHERE device_id = '00008110-000A40A201EBA01E';

COMMIT;
```

Details worth knowing for next time:

- **How I knew the child list was complete:** rather than trusting memory, I queried `information_schema.table_constraints` joined to `constraint_column_usage` for foreign keys referencing `customer_devices(device_id)` — only `ios_device_apps` came back. The no-FK varchar references I knew from the schema files (their comments explain *why* there's no constraint).
- **Ordering matters twice:** the new parent must exist before children move (step 2 after 1), and the old parent must be childless before deletion is *safe-by-inspection* (step 3 after 2 — deleting earlier would have worked but via `ON DELETE CASCADE`, silently destroying the 14 rows you were trying to keep).
- **The alternative** for a one-off like this: `ALTER TABLE ios_device_apps ... DEFERRABLE INITIALLY DEFERRED` on the FK would let you update parent and children in either order within one transaction, with the check deferred to `COMMIT`. Not worth a schema change here, but it's the standard answer when key-renames are a recurring need.
- The `BEFORE INSERT` trigger that normally generates `device_id` respects an explicitly supplied value, which is what makes step 1 possible at all.

There's also a subtle correctness point beyond the SQL: renames like this must leave `mosyle_install_profile_name` agreeing with the actual profile name in Mosyle's UI (the Playwright automation looks profiles up by name), which is why that column kept its `HI_…_install` value through both operations.
