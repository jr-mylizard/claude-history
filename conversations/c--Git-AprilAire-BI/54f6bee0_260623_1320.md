Ok.  So then how do I create and handle the variable in dbt jobs?

---

**Claude**

Since you already have `var('run_cost_snapshot', false)` with a default in the model, you don't need to declare the variable anywhere else in the project — dbt uses the default when it's not passed.

**Hourly job — no change needed.** The variable simply isn't passed, so the default `false` applies.

**Monthly job — add `--vars` to the command in dbt Cloud (or wherever jobs are configured):**

```
dbt build --select Cost_Snapshot --vars '{run_cost_snapshot: true}'
```

In dbt Cloud, this goes in the job's **Commands** field — each command is one line, so the monthly job would have just that one line instead of a generic `dbt build`.

**Re-run** works identically — trigger the monthly job again, same command, same variable. No timing constraints.

---

One thing to keep in mind: if you ever want to run a **full refresh** of the snapshot (rebuild from scratch rather than incrementally merging), that would be:

```
dbt build --select Cost_Snapshot --full-refresh --vars '{run_cost_snapshot: true}'
```

Without `--vars '{run_cost_snapshot: true}'`, a `--full-refresh` would just create an empty table (the `{% else %}` branch), so the variable is always required to get real data.
