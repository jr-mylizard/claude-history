SELECT
    CASE
        WHEN Month = 1 AND workday_of_month = 3 THEN 1
        WHEN Month <> 1 AND workday_of_month = 1 THEN 1
        ELSE 0
    END AS run_cost_snapshot
FROM (
    SELECT
        Workday_Date,
        Month,
        ROW_NUMBER() OVER (PARTITION BY Year, Month ORDER BY Workday_Date) AS workday_of_month

**Claude**

Yes — no extra step needed. Here's why:

dbt's incremental materialization automatically detects when the target table doesn't exist yet. In that case, it ignores incremental logic entirely and does a `CREATE TABLE AS SELECT` using whatever SQL gets compiled — which, with `run_cost_snapshot: true`, is your full source query (the `{% if var(...) %}` branch has no `is_incremental()` filtering inside it, so it always pulls the current full state of `MC_RCTM`).

1. See the table doesn't exist
2. Run the full source query
3. Create the table with those rows

You don't need `--full-refresh` for the first run; that flag is only needed if you ever want to force a rebuild of an *existing* table from scratch.

Two parts to the fix:

**1. Fix the model** so future builds use the right type — wrap the NULLs in an explicit cast (e.g., `VARCHAR(255)`, since they're meant to hold file/table names).

**2. Fix the existing table** — this is the part that has to happen at the database level, sort of. dbt's incremental materialization doesn't `ALTER COLUMN` on existing tables; it just merges into whatever schema is already there. You need to use the inner branches — the outer "Success" connector won't give you the differentiated behavior you want.

Here's why: the If Condition activity itself succeeds as long as it can evaluate the condition, regardless of whether the result was True or False. Then, anything you want to run only after a *confirmed success* should go inside the True branch (not chained off the outer If Condition's success connector), since that outer connector doesn't distinguish the outcome.

Threre's no activity type that branches on "Yes" or "No" vs. "Success" or "Failure"?

**Claude**

Right — **If Condition** (and **Switch**, for more than two branches) are the only activities built for Yes/No-style branching based on evaluating an expression/data value. That's what we used for both the date check and the dbt status check.

Every other activity (Web, Wait, Set Variable, Until, Execute Pipeline, etc.) only exposes **execution-outcome** connectors on its output: Success (green), Failure (red), Skipped, and Completion (fires regardless of outcome). So the two mechanisms are genuinely separate:
- **If Condition / Switch** → branches on *data* (a boolean expression, a status code, a date check)
- **Success/Failure output connectors** → branches on whether the *activity itself* errored out

That's exactly why we needed the explicit `Fail` activity inside the If Condition's False branch earlier — without it, there'd be no way to convert "dbt status was 20 (Error)" (a data fact) into an actual pipeline failure (an execution outcome) that downstream monitoring/alerting would notice.

**Steps:**

1. **Create a new pipeline** — something like `Trigger and Monitor dbt Cost Snapshot`
2. **Cut** the whole chain from "Trigger dbt Job" through "Did DBT Succeed" (including its Fail activity) out of the current pipeline
3. **Paste** that chain into the new child pipeline's main canvas
4. Back in your original pipeline, inside the "Check Date Condition" If Condition's **True** branch, add an **Execute Pipeline** activity (sometimes labeled "Invoke Pipeline") and point it at the new child pipeline
