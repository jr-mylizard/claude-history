**Claude**

Good context. The `Workdays` model has `Is_Workday` and the `Year`/`Month`/`Day` columns from `Workdays_Raw`, but it's missing a within-month rank (workday #1, #2, #3 of the month). That's the key piece needed to implement this schedule.

**Recommended approach: Fabric Data Factory handles the "when", dbt handles the "what"**

Keep the dbt model exactly as-is. In Fabric, add a **Lookup activity** before the dbt activity that queries the Workdays table to decide whether to pass `--vars`:

```sql
SELECT
    CASE
        WHEN Month = 1 AND workday_of_month = 3 THEN 1
        WHEN Month <> 1 AND workday_of_month = 1 THEN 1
        ELSE 0
    END AS run_cost_snapshot
FROM (
    SELECT
        Workday_Date,
        Month,
        ROW_NUMBER() OVER (PARTITION BY Year, Month ORDER BY Workday_Date) AS workday_of_month
    FROM Silver.Workdays
    WHERE Is_Workday = 1
) w
WHERE w.Workday_Date = CAST(GETDATE() AS DATE)
```

Then an **If Condition activity** branches on `@equals(activity('Lookup').output.firstRow.run_cost_snapshot, 1)`:

- **True:** Run dbt with `--vars '{run_cost_snapshot: true}'`
- **False:** Run dbt normally (no vars)

If today isn't a workday at all, the Lookup returns no rows — you'd want to handle that as a False branch too (check `activity('Lookup').output.count` first).

This keeps scheduling logic in the orchestrator where it belongs, and the dbt model stays simple and independently testable. Does this match how your Fabric pipelines are currently structured?
