---

## Problem
Independently verify, per device, that MDM actions actually took effect — without relying solely on the MDM console's own report of itself. Two distinct sub-problems with different constraints:

1. **App install/removal verification** — trusted for Android (Hexnode), open concern for iOS.
2. **Website blocking verification** — need to confirm a device *cannot* reach specific blocked domains, from wherever the device actually is, remotely.

## Findings

### iOS app verification — no path to full independent inventory
Apple sandboxes apps from seeing what else is installed; no third-party (non-jailbroken, no-USB) tool can enumerate the full app list. The only source of a complete inventory is the MDM protocol itself (`InstalledApplicationList`) — which is what Mosyle's console already reports, and what `mosyle_device_check.py` already reads via `device_apps.php`. There is no independent full-inventory alternative to cross-check Mosyle's own answer; **"trust Mosyle's report" is the ceiling**, not a stopgap.

What *is* achievable independently is a **spot-check**, not a full audit: iOS Shortcuts can test whether a specific app is installed via its custom URL scheme (`canOpenURL`-equivalent — "Open URL" and check whether it left Shortcuts). This only covers apps that register a scheme (most consumer apps do, but needs confirming per app) and only tells you yes/no for apps you explicitly list — useful as a second opinion on specific adds/removals you just pushed, not a general audit.

### Website blocking verification — needs an on-device check, not a cloud one
This is fundamentally different from app checks: it's live network behavior, not static state, so nothing server-side can answer it — generic uptime tools (Pingdom, UptimeRobot, etc.) check from their own cloud servers, not from the phone sitting behind Mosyle's DNS/content-filtering profile, so they're not applicable here regardless of platform.

The only real option is code that **runs on the device** and makes the actual request:
- **iOS**: a Shortcuts personal automation (scheduled, "Ask Before Running" off) running "Get Contents of URL" against each domain in the blocklist, capturing success/status/timeout, then POSTing the results to a Supabase edge function. Runs natively, no extra app needed, tests the device's real current network path.
- **Android**: same idea via Tasker or Termux+cron.

**Trigger-model caveat, both platforms:** none of these can be pushed to run "right now" from a server on stock tooling — Shortcuts runs on a schedule/event, not a remote command. Android can get closer to on-demand (Tasker can react to a push via something like ntfy/AutoRemote), iOS cannot without a real app receiving a silent APNs push. For validation purposes, "runs every 15–30 min, check the latest result after making a change" is probably sufficient — worth confirming that's an acceptable latency before ruling it out.

### The unifying long-term option
A minimal custom companion app (iOS + Android, internal/TestFlight distribution) that receives a silent push and immediately runs both the URL-scheme spot-checks and the URL-reachability checks, reporting back on demand. Same sandbox ceiling as Shortcuts for iOS app-inventory (still spot-check only, not full enumeration), but gives true on-demand triggering and one unified tool instead of two platform-specific automations. Highest effort, not needed to get started.

## Recommended task breakdown
1. **Website blocking validation (both platforms)** — build the Shortcuts automation (iOS) and Tasker/Termux script (Android) that hit the blocklist domains on a schedule and POST results to a new Supabase edge function. This is the higher-value, more tractable piece and needs no new backend concepts.
2. **iOS app spot-check** — Shortcuts automation testing URL schemes for a curated list of apps you're actively adding/removing via MDM; confirm which target apps actually expose a scheme first.
3. **(Stretch/later)** Custom companion app for on-demand push-triggered checks, if the scheduled-automation latency proves insufficient in practice.
4. Decide and document: for iOS full app-inventory, formally accept Mosyle's `InstalledApplicationList` report as ground truth (no independent alternative exists) — worth checking whether Mosyle's data reflects a live on-demand device check-in or a cached/periodic one, since that affects how quickly a push can be confirmed.
