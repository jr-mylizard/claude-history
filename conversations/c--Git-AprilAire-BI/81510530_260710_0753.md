**Claude**

Because the crash was a runtime `TypeError` on `null`, not a logic error — and the null only existed in that one row.

Before the fix, the code built each item as `label: a.name`. TypeScript declared `name: string` (non-nullable), so it allowed `a.name` directly. But at runtime `a.name` was `null` for the orphan row, making `label: null`. When you typed a character, the filter ran `it.label.toLowerCase()` on every item — and the moment it hit the orphan's `null` label it threw `TypeError: Cannot read properties of null`, crashing the page.

Every other row in the table had a real name string, so the filter never touched a null. Once you deleted the orphan, all labels were valid strings again, and the filter ran cleanly — same broken code, no bad data to trigger it.

The code fix (`(it.label ?? "").toLowerCase()`) just makes it so this can never happen again if another null-name row appears in the future. The data fix was sufficient for the immediate symptom; the code fix is the safety net.

**Claude**

Yes, and here's why it's the right call: the Add App button should only be enabled when the user has selected a result from the dropdown, not just typed something into the search box.

The trade-off is minor: a power user who knows a bundle ID by heart can't bypass the search — but the server action validates via iTunes anyway, so they'd just get a server-side rejection instead. The upside is you fail fast in the UI with zero round-trip, and you eliminate the entire class of problem where a raw string gets submitted, the iTunes lookup returns nothing, and you end up with a null-name row.

Concretely: the button should be disabled until the user has picked an item from the search results. The state distinction is **text in the input** vs **selection confirmed from results**. Most autocomplete-style inputs model this with a separate `selectedApp` state (cleared on every keystroke, set on item click) — the button gates on `selectedApp !== null`.
