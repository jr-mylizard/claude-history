## 1. What kind of DNS routing belongs in a mobileconfig?

On iOS there is **no payload for setting plain IP DNS servers system-wide**. The only MDM mechanism is the encrypted-DNS payload `com.apple.dnsSettings.managed` (iOS 14+), which supports exactly two protocols: **DoH (`HTTPS`)** or **DoT (`TLS`)**. Classic IP-address DNS can only be set per-network by hand on the device, so for your use case DoH/DoT is the right (and only) choice. DoH is generally preferred over DoT because it runs over TCP 443 and survives restrictive networks that block port 853.

**The big gotcha (likely why the intern's test "didn't work"):** Apple's own schema states verbatim: *"When installed from an MDM, the setting only applies to managed Wi-Fi networks. When installed manually, this setting also applies to cellular networks."* So a DNS payload pushed through Mosyle will **not filter cellular traffic**, and per the docs applies only to *managed* Wi-Fi networks. If the intern tested on cellular or on a hand-joined Wi-Fi network, filtering would appear completely dead. If cellular enforcement is a hard requirement, the standard workarounds are a content-filter payload (`com.apple.webcontent-filter`, supervised — but Safari/WebKit only), an always-on VPN, or a DNS-proxy app — none as simple as the DoH payload.

## 2. Formatting — and two probable bugs in `dns.mobileconfig-part`

The structure in [dns.mobileconfig-part](../MyLizard-Supabase/mosyle/dns.mobileconfig-part) is mostly right. Schema for the `DNSSettings` dict:

- `DNSProtocol` (required): `HTTPS` or `TLS`
- `ServerURL` (required for HTTPS): the RFC 8484 DoH URL
- `ServerName` (required for TLS only): hostname for cert validation
- `ServerAddresses` (optional): IPs used to **reach the DoH/DoT server itself** without a bootstrap DNS lookup
- `SupplementalMatchDomains`, `OnDemandRules` (optional scoping)
- `ProhibitDisablement` (supervised only): prevents the user from toggling encrypted DNS off in Settings

Issues I see in the current snippet:

1. **`ServerAddresses` is probably wrong.** It lists `185.228.168.85` / `185.228.169.85` — CleanBrowsing's *plain-DNS* filter IPs. In this payload, `ServerAddresses` isn't "fallback classic DNS"; it tells the device "connect to these IPs to reach the DoH endpoint." If those IPs don't serve HTTPS DoH for `doh.cleanbrowsing.org`, resolution can fail outright. Since the key is optional, the safe fix is to **delete `ServerAddresses` entirely** and let the device resolve the DoH hostname normally.
2. **`ProhibitDisablement` is missing.** Without it, the child can go to Settings → General → VPN & Device Management and toggle the encrypted-DNS profile off. Your devices are supervised, so add `<key>ProhibitDisablement</key><true/>`.

Corrected payload dict:

## 3. Can multiple mobileconfig files coexist on one device?

**Yes — this is the normal model.** iOS happily installs many configuration profiles side by side, and Apple's deployment guide explicitly says multiple DNS Settings payloads may be delivered to a device. Rules of thumb:

- **Restrictions merge most-restrictively**: if two profiles set the same restriction, the stricter value wins.
- Each profile needs a **unique `PayloadIdentifier`** (top level); re-pushing the same identifier replaces that profile rather than duplicating it, which is how updates work.
- I'd keep DNS in its **own separate profile** rather than merging it into `mylizard.mobileconfig` — you can then update, remove, or troubleshoot filtering independently of the app whitelist, and Mosyle treats each custom profile as its own deployable unit.

**Recommended next test protocol:** push the corrected standalone DNS profile from Mosyle, put the device on a *managed* Wi-Fi network (one whose Wi-Fi payload also came from Mosyle), then check https://1.1.1.1/help or CleanBrowsing's test page. Then repeat on cellular to confirm (and document) the cellular gap before deciding whether you need a content-filter or VPN payload to cover it.

Why would proxy filtering work on all networks, but DNS only on managed wifi networks?

---

**Claude**

It comes down to *where* each mechanism lives in iOS's networking architecture — one is a per-network **setting**, the other is code sitting inside the **network stack itself**.

**The DNS Settings payload is configuration data attached to networks.** `com.apple.dnsSettings.managed` doesn't run anything; it just tells the OS "when resolving on network X, use this resolver." Resolver settings in iOS are properties of a network configuration, and MDM's authority over network configurations only extends to the networks it actually manages — the Wi-Fi networks it pushed via Wi-Fi payloads. The cellular data configuration belongs to the carrier and the user, and a hand-joined home Wi-Fi network is a user-created configuration, so an MDM-delivered setting doesn't attach to them. (When the *user* installs the same profile manually, that's treated as explicit personal consent to change their own device-wide resolver — which is why manual install covers cellular but MDM push doesn't. That part is a deliberate Apple policy line, not a technical impossibility.)

**Proxy and filter payloads install a NetworkExtension, not a setting.** `com.apple.dnsProxy.managed` (NEDNSProxyProvider) and `com.apple.webcontent-filter` (NEFilterDataProvider) cause an on-device extension — real code, usually shipped inside an app — to be inserted into the network stack. Traffic is intercepted at the socket/flow level *before* it's handed to any particular interface, so it's inherently interface-agnostic: Wi-Fi, cellular, hotspot, VPN — the extension sees the flows regardless of what network they'll eventually ride on. There's no per-network attachment point to be scoped by.

Apple gates that much more powerful capability behind a higher trust bar: DNS proxy and content-filter payloads require a **supervised** device (and for DNS proxy, an app you control containing the extension). The implicit deal is: per-network settings are low-trust and therefore scoped narrowly; stack-level interception is high-trust (supervision = the org owns the device) and therefore allowed to be global.

Practical consequence for you: since your devices are supervised, you *can* get all-network DNS filtering, but not with a bare mobileconfig — the DNS-proxy route requires shipping a NEDNSProxyProvider inside an app deployed to the device. The lighter options remain the web content filter payload (all networks, but WebKit-scoped) or checking whether CleanBrowsing offers an iOS filtering app/extension that Mosyle can deploy alongside a config.

## Mapping Mosyle's UI to Apple's payloads

**"DNS Settings" profile** = `com.apple.dnsSettings.managed` — the DoH/DoT payload your intern was testing. All the limitations I found apply: managed-Wi-Fi-only when MDM-pushed, no cellular coverage, bypassable by browsers that bring their own resolver.

**"DNS Proxy Extension" profile** = `com.apple.dnsProxy.managed` — the payload that *activates* a `NEDNSProxyProvider` network extension living inside an app on the device. The payload is just a pointer (app bundle ID + provider bundle ID); it's useless without an app that contains the extension. This is the all-networks mechanism.

**"Web Filter" profile** = `com.apple.webcontent-filter` — supervised-only, all networks, but WebKit-scoped on iOS (Safari and in-app web views; it doesn't see arbitrary app traffic).

**The separate "DNS Filtering" section** is not a raw payload at all — it's Mosyle's own managed filtering *product*, and the three notes you quoted are strong evidence of how it works under the hood:

1. **The Private Relay note tells you Mosyle controls the resolver.** The Apple page they link describes exactly one blocking procedure: refuse to resolve `mask.icloud.com` and `mask-h2.icloud.com`, which signals to the device that the network doesn't permit Private Relay (hence the "network is not compatible" prompt users see). You can only "implement the blocking procedures described here" if *you are the DNS resolver* — so Mosyle DNS Filtering routes queries to Mosyle-operated resolvers, not to a third party like CleanBrowsing.

2. **The third-party-browser note tells you it's endpoint/extension-based, not settings-based.** A bare `dnsSettings` payload can't do anything about Firefox or Chrome using their own built-in DoH — that traffic never touches the system resolver. Mosyle's claim of "Endpoint-only based Web Content Filtering" combined with their auto-installed agent app means they intercept at the network-extension level on the device. That's why the DNS Filtering section is "applied differently" than the profiles section — it's almost certainly Mosyle pushing a DNS Proxy Extension (and/or content-filter) profile that points at *their own agent app*, which is why the agent installs automatically with MDM.

3. **The captive-portal bypass option confirms they've productized the classic failure modes.** Forced encrypted DNS breaks hotel/airplane portal logins (the portal needs local DNS resolution to hijack you to its login page). Their per-domain bypass is the managed equivalent of the `OnDemandRules`/`SupplementalMatchDomains` escape hatches in the raw payload.

## What this tells you about Mosyle's capabilities — and your decision

The practical picture that emerges:

- **Mosyle DNS Filtering solves both problems the raw DNS Settings payload has** — it works on all networks including cellular (because it's a DNS proxy extension, not a per-network setting) and it defeats the two big bypass vectors (Private Relay, browser DoH). This is very likely the *only* Mosyle option that gives you cellular filtering without you shipping your own NetworkExtension app.
- **The trade is control-plane, not capability:** DNS Filtering is UI-only (no API), so parameterizing it per-device means extending your existing Playwright automation in [scripts/mosyle/](../MyLizard-Supabase/scripts/mosyle/) — and it uses Mosyle's resolvers and category rules, so CleanBrowsing's custom filter profile drops out of the picture.
- **The raw "DNS Settings" profile remains the automatable option** (API-manageable, parameterizable like your app whitelist), but only if you accept managed-Wi-Fi-only coverage — which for kids' iPhones on cellular is probably disqualifying on its own.
- The "DNS Proxy Extension" profile type existing in the UI *suggests* you could point it at a third-party filtering vendor's app if that vendor ships an iOS DNS proxy extension, but that requires deploying that vendor's app too. It won't do anything pointed at nothing.

Two cheap hardening moves worth doing **regardless of which path you pick**, in your existing restrictions payload in [mylizard.mobileconfig](../MyLizard-Supabase/mosyle/mylizard.mobileconfig): you already have `allowVPNCreation` = false (blocks VPN-based bypass); consider adding `allowCloudPrivateRelay` = false (supervised restriction that kills Private Relay outright, cleaner than the DNS-blocking dance and useful even with Mosyle's own blocking as belt-and-suspenders).

**Yes — but "configurable" works differently than you might expect.** The DNS Proxy payload (`com.apple.dnsProxy.managed`) has only three meaningful keys:

- `AppBundleIdentifier` — the app containing the extension (must be installed on the device, e.g. pushed via Mosyle's Install App)
- `ProviderBundleIdentifier` — the extension inside that app
- `ProviderConfiguration` — an **arbitrary vendor-defined dictionary** handed to the extension at startup

So there's no standard "resolver address" key. Resolver addresses, org IDs, policy tokens, per-device identifiers — all of that goes in `ProviderConfiguration`, and its schema is whatever the vendor's extension reads. Cisco's, for example, takes keys like `organizationId` and a registration token. This is good news for your architecture: `ProviderConfiguration` values are plain strings in the mobileconfig, so **Mosyle custom variables (`%custom_XXXX%`) should be substitutable there**, the same trick you're using for the app whitelist — letting you parameterize per-device filtering identity if the vendor's schema supports a per-device token. iOS requires supervision for DNS proxy payloads, which you have.

Short answer on the Web Filter question: **it can add blocks, but it cannot add allows — and the allow direction is the one you'd want it for.**

## Why Web Filter can't override a DNS block

The two mechanisms operate at different layers, in sequence. Mosyle's DNS filtering decides whether a domain *resolves at all*; the Web Filter payload (`com.apple.webcontent-filter`) inspects URLs inside WebKit *after* resolution. A `PermittedURLs`/allowlist entry in the Web Filter only relaxes Apple's **built-in auto-filter** — it can't resurrect a domain whose DNS lookup returns a block page IP or NXDOMAIN. The page simply never loads, allowlist or not. The reverse layering does work (`DeniedURLs` would block a site Mosyle's DNS allows), but it's WebKit-scoped, it's the wrong tool, and it's exactly the "other web filtering profile" Mosyle tells you to remove — likely because stacked filters produce confusing behavior and support tickets, not because they technically conflict.

**Consequence for your extension plan:** per-parent "always allow example.com" must live inside Mosyle's DNS Filtering Allowed/Blocked tab — which is the UI-only part. So a custom exception means cloning one of the 33 profiles plus a device group, via Playwright or by hand. That's fine as a low-volume support workflow, but it can't be a self-serve parent feature without Playwright automation. Worth deciding now which one it is.

## The thing you're actually missing: Mosyle DNS Filtering isn't free

Your cost comparison assumes the Mosyle option costs nothing incremental. Search results indicate DNS Filtering is bundled in the **Fuse tier at $3/device/month**, while base Mosyle Business is $1/device/month (Business + Security at $1.50 sits between; which tier first includes DNS Filtering is worth confirming with Mosyle). If you're on base Business today and DNS Filtering requires Fuse, the *marginal* cost is $1.50–$2/device/month — which makes DNSFilter's flat $1 the *cheaper* option, inverting your conclusion. If you're already committed to Fuse for other reasons (EDR, SSO), then it's genuinely $0 marginal and your reasoning holds. This is the number to pin down before building 33 profiles.

On Cloudflare: the current structure is **free up to 50 users, then $7/user/month with no partial billing** — so it will never meet your $0.50 bar at scale. It's only interesting as a $0 option while you're under ~50 families, with a painful cliff after.

## Smaller gaps worth closing

- **Verify the API actually moves devices between device groups** under your rate limits (your Mosyle API surface has been limited before — silent save refusals, `/adminlogs` quirks). The whole 33-policy architecture rests on this one call working reliably.
- **Exclusive group membership**: decide what happens if a device lands in two filtering groups — Mosyle's profile precedence there is undocumented. Your assignment code should enforce exactly-one-group, and you should test that *leaving* a group promptly removes its profile (including for offline devices that reconnect later).
- **Test cellular empirically** before committing — the all-networks behavior of Mosyle's DNS Filtering is my inference from their Private Relay/endpoint language, not something they state outright.
- **Remove the CleanBrowsing DoH profile** from test devices before enabling (that's precisely what their warning targets), and add `allowCloudPrivateRelay` = false to your restrictions payload as belt-and-suspenders.
