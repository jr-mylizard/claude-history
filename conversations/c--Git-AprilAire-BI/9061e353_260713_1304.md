I grounded it in the actual code (`sync-mosyle.ts`, the desired-state view, the `ios_device_apps` table, the 393 KB mobileconfig) plus live data from the dev branch. The key decisions it proposes:

**Core design** — a fixed pool of 500 per-device slot CDAs (`custom_AS0001`–`custom_AS0500`, new prefix so legacy `custom_AA*` can coexist during migration). Each `ios_device_apps` row gets a `slot` number, unique per device, allocated by a trigger on insert and **stable for the row's lifetime** — schedule on/off toggles keep today's exact assign/revoke mechanic and never reallocate slots. App ids become irrelevant to Mosyle: no 9999 ceiling, no lpad coupling, and the MTZ LIFE renumbering is obsoleted entirely.

**Sizing** — the dev device has 158 catalog rows (the observed max), so 500 slots is ~3x headroom, and the profile shrinks from 393 KB / 9,999 entries to ~20 KB. A `CHECK (slot BETWEEN 1 AND 500)` makes the DB refuse to hand out a slot the profile doesn't cover — the exact silent failure that bit us with 5-digit app ids.

**What changes in sync-mosyle** — the per-app device batching goes away (each device now has its own value per CDA), `reset` becomes delete + recreate-with-first-device + per-device assigns (still avoiding Mosyle's lowercase-normalizing update call), and step-5 cleanup needs prefix guards plus throttling for the ~200 legacy CDA deletes at cutover.

**Migration** — big-bang rather than dual-write, since the fleet is one device: schema → slot-aware sync + regenerated profile → `reset=true` + bounce. Your held-back apps are the validation plan: MTZ LIFE proving the 5-digit ceiling is gone with no renumbering, Uber's visibility check, and read-back confirmation that `custom_AA1250`/`custom_AA4269` get garbage-collected.
