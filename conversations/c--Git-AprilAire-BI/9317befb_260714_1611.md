## Report

**1. Where `device_app_categories` rows get populated**

`device_app_categories` is **not a table** — since migration `supabase/migrations/20260522000009_drop_and_replace_scheduling.sql` (+ `20260523000002_cleanup_dead_triggers.sql`), it's a **computed VIEW** (`supabase/schemas/20 Views/202 Device/20206 device_app_categories.sql`, view def lines 8-65). It aggregates live from `android_device_apps`/`android_apps` and joins schedule names from `device_category_schedules` + `device_schedules`. There's nothing to "insert" into it anymore — its old trigger-based populate function (`.ml_device_app_categories_populate`, triggers in `supabase/migrations/20260409203025_streamline_device_app_categories_populate.sql:14-163`) was dropped along with the table.

What Android enrollment actually creates today:
- `supabase/functions/pre-enrollment-device-setup/pre-enrollment-android.ts`, **Step 3b (lines 136-164)**: creates a single `device_schedules` row named `"Always"` for the device plus 7 `device_schedule_blocks` rows (`00:00:00`–`23:59:59`, all days). This is idempotent (checks for existing "Always" first, lines 139-145).
- Nothing else in `pre-enrollment-android.ts` or `post-enrollment-android.ts` writes to `device_category_schedules`.
- By contrast, iOS's `pre-enrollment-ios.ts` **Step 6b (lines 514-530)** does upsert `device_category_schedules` rows linking resolved app categories to the "Always" schedule — Android has no equivalent step.

**2. Default schedule values per category**

There is **no hardcoded default schedule map** for categories anywhere in migrations/schemas/functions — no code assigns `"Always"` (or anything) to `Entertainment`, `Game Puzzle`, `Libraries and Demo`, `Tools Advanced`, or any `"Vendor ..."` category. In fact none of the literal strings `Vendor AT&amp;T`, `Vendor Verizon`, `Vendor Motorola`, `Vendor Boost`, `Vendor Cricket`, `Vendor MetroPCS`, `Vendor T-Mobile`, `Vendor Tmobile`, `Vendor TracFone`, `Libraries and Demo`, or `Tools Advanced` appear anywhere in the repo. The only category→schedule assignments in the codebase are one-off hand-written backfill scripts for specific real customer devices (`scripts/migrate_to_prod/scheduling.sql`, `scripts/migrate_to_prod/android_device_WI_608A_*.sql`, `scripts/migrate_jr_device_to_dev.sql`), and even there the same category gets different schedules per device (e.g. `Game Puzzle` → `"Free Time"` for one device, `"Always"` for another — `scheduling.sql:83` vs `:118`). Categories left out of these VALUES lists get no schedule row at all, meaning (per `vw_desired_hexnode_app_groups_state`/`vw_desired_mosyle_cdas_state`) those apps are treated as disabled/never-allowed by design when unscheduled — not an accidental gap.

**3. Backfill/re-run utility**

None exists as a general-purpose function. `pre-enrollment-android.ts` Step 3b can safely be re-run for an already-enrolled device (idempotent) but only ensures the `"Always"` schedule/blocks exist — it never touches `device_category_schedules`, so it cannot fix category assignments. The only precedent for backfilling `device_category_schedules` is the hand-crafted, device-specific SQL scripts in `scripts/migrate_to_prod/`, or manual entry via the WeWeb calendar UI (per the comment in `scheduling.sql:10-12`). Today this would have to be done by hand — there's no reusable "re-run enrollment defaults" entrypoint.

That "is_in_play_store" flag is exactly the gate. Here's the actual rule from the view's header comment (`vw_desired_hexnode_app_groups_state.sql:7-12`):

> Apps are enabled if: (1) category has an active schedule, (2) `is_necessary` is true, OR (3) **`is_system_app` is true AND `is_in_play_store` is false**.

So today, a system app only gets auto-enabled if it has *no* Play Store listing. Every app you flagged (AT&T ActiveArmor, Verizon Protect, Prime Video, Moto Camera, etc.) is `is_system_app: true` but also `is_in_play_store: true` — so rule 3 doesn't cover them, and with no category schedule either, they stay disabled. That's not a bug or a missed enrollment step; it's this exact condition working as written.

If "we just enable system apps all the time" is the policy you want, the fix is dropping the `is_in_play_store IS NOT TRUE` condition from rule 3 — but that's a one-line change to a shared view, so it would immediately flip every currently-blacklisted system app (carrier bloatware included — AT&T, Verizon, Cricket, T-Mobile, Boost, MetroPCS apps) to enabled on **every** Android device in the fleet, not just this one.
