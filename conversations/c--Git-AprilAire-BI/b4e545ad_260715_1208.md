## Root cause #1 (primary): near-invisible modal content when a device has no schedules yet

`editingCategory` and `editingWebCat` both render their body as:

```tsx
// DeviceManagement.tsx:1280-1296 (editingWebCat) and :1308-1324 (editingCategory)
&lt;div className="space-y-1"&gt;
  {schedules.map(s =&gt; { ... })}
&lt;/div&gt;
```

`schedules` comes from `loadCalendarEvents` → `dm.getCalendarData(deviceId)`. In `src/app/actions/deviceManagement.ts:76-84`:

```ts
const { data: schData } = await supabase.from("device_schedules").select("id, name").eq("device_id", deviceId)
const schedules = (schData ?? []) as Schedule[]
if (schedules.length === 0) {
  return { schedules, blocks: [], colors: [], categoryScheduleRows: [] }
}
```

There is no default/auto-created schedule (e.g. no "Always" row seeded per device), so **a brand-new device genuinely has `schedules = []`**. When that's true and the user clicks "+ Edit" on any Category/Website row (`DeviceManagement.tsx:1026` or `:1104`), the modal opens, but its body renders **nothing** — just a tiny header line (category name + "×") inside a `w-72` box that uses `bg-background` (the same color family as the page). Meanwhile the `bg-black/30` backdrop (`fixed inset-0 z-50`) darkens the *entire* viewport.

Net visual effect: the whole page dims, and the only "modal" on screen is a barely-noticeable, content-less, page-colored sliver dead-center of the screen — exactly the "dark/grey, like there's a popup but there's no popup" symptom reported.

## Root cause #2 (contributing): modal state is never reset, and isn't scoped to the tab it belongs to

The three modal state variables:

```tsx
// DeviceManagement.tsx:486, 495-496
const [popup, setPopup] = useState&lt;PopupState&gt;(null)
...
const [editingCategory, setEditingCategory] = useState&lt;string | null&gt;(null)
const [editingWebCat, setEditingWebCat] = useState&lt;string | null&gt;(null)
```

are only ever cleared by their own explicit close handlers (backdrop `onClick`, the "×" button, or a successful save/delete). They are **not** reset by:
- the customer-change effect (`DeviceManagement.tsx:607-624`)
- the device-change effect (`DeviceManagement.tsx:627-654`)
- the tab-switch effect (`DeviceManagement.tsx:659-668`)

and the JSX for all three modals is rendered as **top-level siblings after the tab-content `&lt;div&gt;`** (`DeviceManagement.tsx:982-1272` is the tab content; the modals are at `:1273`, `:1301`, `:1329`), i.e. they are not gated by `tab === "..."` at all. Nothing prevents an "orphaned" backdrop from persisting if the state doesn't get cleared through the normal click path (e.g. changing the Device/Customer `&lt;Select&gt;` via keyboard while a modal is open never touches the backdrop's `onClick`). None of the three modals have an Escape-key handler either, so there's no fallback way to dismiss a stuck one. This isn't the everyday trigger, but it compounds the same visible failure mode (dark backdrop, unnoticed/absent-looking content).

## Recommended fixes

1. **Give the empty-schedules state a visible presence** in `editingCategory`/`editingWebCat` (`DeviceManagement.tsx:1280-1296`, `:1308-1324`): when `schedules.length === 0`, render an explicit message, e.g. `"No schedules yet — create one from the Calendar tab."` instead of an empty `&lt;div&gt;`. This alone fixes the reported symptom in the most common real case.
2. **Reset `popup`, `editingCategory`, `editingWebCat` to `null`** whenever `deviceId`, `customerId`, or `tab` changes (add to the effects at `DeviceManagement.tsx:607-624`, `:627-654`, `:659-668`), so a modal can never survive a navigation action.
3. **Add an Escape-key handler** to all three modals (or centralize them into one reusable `Modal` component that wires this once) so users always have a guaranteed way to dismiss a backdrop even if a click doesn't land on it.
4. Longer-term: extract the duplicated `fixed inset-0 z-50 ... bg-black/30` + content wrapper into a single shared `Modal` component used by `SchedulePopup`, `editingCategory`, and `editingWebCat`, so backdrop-visibility and content-visibility can never drift apart the way they did here (they currently only avoid it by discipline/copy-paste, not by structure).

## P0 — High severity, public-facing, sits directly above interactive elements

### 1. `SolutionPage.tsx` hero image — declared aspect ratio is backwards (portrait vs. actual landscape), on every `/solutions/[slug]` page
**File:** `src/components/solutions/SolutionPage.tsx:70-77`
```tsx
&lt;Image
  src={config.imageSrc}
  alt={config.heading ?? ""}
  width={960}
  height={1280}
  className="w-full h-auto object-cover"
  sizes="(max-width: 768px) 100vw, 480px"
/&gt;
```
- Declared ratio: `960/1280 = 0.75` (portrait).
- Actual files (checked all 5 used by `src/lib/solutions.ts`): `Mennonites.jpg` 2698×1800, `Grandfather and child.jpg` 5760×3840, `Woman journal.jpg` 6000×4000, `Woman with kids.jpg` 5472×3648 — **all ≈1.5 ratio (landscape)**. `App Scheduler.png` is 995×1162 (≈0.86), also off.
- Because the element is `w-full h-auto`, the browser reserves height using the *declared* ratio (0.75 → tall box), then once the image loads the browser's CSS `aspect-ratio: auto` resolution switches to the *natural* ratio (1.5), and the box height roughly **halves**. This affects `/solutions/schools`, `/solutions/religious-groups`, `/solutions/grandparents`, `/solutions/adults`, `/solutions/parents` — all public marketing pages.
- Below this image on the same page (`SolutionPage.tsx:83-107`) sits either the `SchedulerSection` (a `ContactForm` with input fields + submit button) or the `FeaturedListingCard` grid (clickable product links) or the FAQ accordion — exactly the "I click and it moves because something loaded" scenario, since the shift happens right as the page becomes interactive.
- **Fix:** Set `width`/`height` to match the true asset ratio (roughly 3:2, e.g. `width={960} height={640}`), or better, run each image through `sharp`/an image tool to get exact per-image dimensions since they vary slightly; alternatively wrap in a fixed-aspect container (`aspect-[3/2]`) and use `fill` + `object-cover` so the box is CSS-defined and immune to intrinsic-size mismatches.

### 2. Contact page hero photo aspect-ratio mismatch, directly above the contact form
**File:** `src/app/(marketing)/contact/page.tsx:23-31`
```tsx
&lt;Image
  src="/Booth_Wide.png"
  alt="Jeremiah Robinson at a MyLizard event"
  width={600}
  height={400}
  className="w-full h-auto rounded-xl"
  sizes="(max-width: 768px) 100vw, 468px"
  priority
/&gt;
```
- Declared ratio `600/400 = 1.5`; actual file `Booth_Wide.png` is 4080×1997 → ratio `2.04`. The reserved box is taller than the real image, so once it loads the box shrinks and the content below (`&lt;div className="space-y-4"&gt;` containing the contact/message form, `src/app/(marketing)/contact/page.tsx:32+`) jumps upward. `priority` mitigates the *timing* (loads early) but does not fix the *magnitude* of the shift once it resolves.
- **Fix:** `width={600} height={294}` (or compute per-image via a build script), or convert to `fill` inside an `aspect-[2.04/1]` container.

A few options in Power Automate, best to weakest:

1. **Environment variable (type: Secret)** — if you're in a solution-aware/Dataverse environment, add an environment variable and set its type to **Secret** rather than Text. This is the standard first-class option and what I'd default to.

2. **Azure Key Vault connector** — if you already use Key Vault elsewhere, add a "Get secret" action from the Azure Key Vault connector at the start of the flow, and feed its output into the HTTP action's Authorization header. Keeps the value out of Power Automate entirely except at runtime.

3. **Custom connector with a securestring connection parameter** — if you're calling the Supabase function through a custom connector rather than a raw HTTP action, define the key as a connection-level parameter (type `securestring`). You enter it once when creating the connection; it's encrypted and never shown again in the designer.

**Avoid:** pasting the secret key directly into the HTTP action's header field in the flow designer. That stores it in plaintext in the flow's JSON definition — visible to anyone with read/export access to the flow, and potentially visible in run history too.

If your environment isn't Dataverse-backed (no solution/environment variables available), Key Vault connector is the fallback. Given this is the Supabase service_role/secret key — full-access credential — I'd treat it the same way you're treating `supabase_bearer_token` in Vault for pg_cron: worth actually using Key Vault or a rotated dedicated key rather than the raw service_role key, so a leaked flow doesn't hand out full database access.

Where can I find environment variables in Power Automate?  What is a solution-aware/dataverse environment?

---

**Claude**

**Where to find them:** Environment variables aren't in the regular Power Automate flow editor — they live inside a **Solution**. Go to make.powerautomate.com (or make.powerapps.com, same underlying platform) → left nav **Solutions** → open an existing solution or create a new one → **+ New** → **More** → **Environment variable**. Set its type to **Secret** and give it a value there. To use it inside a flow, add the **"Get an environment variable value"** action — but that action is only available in flows that live *inside* a solution.

**What "solution-aware / Dataverse environment" means:**

- **Environment** = a workspace/container in Power Platform (e.g. Dev, Prod) with its own apps, flows, connections, data. Every tenant has at least one default environment.
- **Dataverse** = Power Platform's built-in database. Not every environment has it — a lightweight environment can exist with no Dataverse at all, used only for simple standalone flows. This matters because environment variables and connection references are Dataverse-backed features — no Dataverse, no environment variables, period.
- **Solution** = a packaging container for grouping related components (flows, connectors, environment variables) so they can be moved between environments as a unit (Dev → Test → Prod), Microsoft's version of a deployment pipeline for this tooling.
- **"Solution-aware" flow** = a flow created *inside* a solution, as opposed to a personal flow sitting in "My flows" outside any solution. Only solution-aware flows can reference environment variables.

**Practically, check first:** does your environment have Dataverse? In make.powerapps.com, look for a "Tables" section in the left nav — if it's there and usable (not grayed out/prompting to add Dataverse), you have it. If your flow currently lives in "My flows" rather than a Solution, you'd need to either move it into a solution or rebuild it there.

**If you don't have Dataverse** (common on lighter M365 tenants), environment variables aren't an option at all — fall back to the Azure Key Vault connector instead, which works in any environment/flow with no Dataverse or solution requirement.
