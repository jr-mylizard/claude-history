This is a **manual download+import workflow** — no Google API calls; the user downloads the `.vcf` and imports it into the phone's Contacts app, selecting the MyLizard Google account as destination (per the file's header comment). Looks up `sms_contacts` by phone for `contact_id`, inserts a `pending` row into `sms_messages`, then calls the **Android SMS Gateway cloud relay** (`https://api.sms-gate.app/3rdparty/v1/messages`, Basic auth via `SMS_GATEWAY_USERNAME/PASSWORD`, optional `SMS_GATEWAY_DEVICE_ID`), updating the message row to `sent`/`failed`.
- **`supabase\functions\sms-webhook\index.ts`** — POST receiver for sms-gate.app webhook events (`sms:received`, `sms:sent`, `sms:delivered`, `sms:failed`). On `sms:received`: looks up the contact by phone, inserts into `sms_messages`, then **forwards the inbound SMS as an email** via Resend (`RESEND_API_KEY`, from `RESEND_FROM_EMAIL`) to `SMS_FORWARD_TO_EMAIL`, setting `reply_to` to `{sms_handle}@waxenua.resend.app` so a reply can be routed back.
- **`supabase\functions\resend-webhook\index.ts`** — the reverse leg of the email gateway. On Resend's `email.received` event (a reply sent to `{handle}@waxenua.resend.app`), it extracts the handle from the recipient address, looks up `sms_contacts` by `sms_handle`, fetches the raw email body via Resend's `/emails/receiving/{id}` API, strips quoted-reply text (Outlook/Gmail/Apple Mail markers), then POSTs the cleaned text to sms-gate.app to send it as SMS to the contact's phone, and logs an outbound row in `sms_messages`. This same file also handles unrelated Resend events (`email.bounced`, `email.complained`, `email.opened`, `email.clicked`) for the separate email-campaign/`contacts`/`email_log` system — those are not SMS-related.

Is there a reason to consider not using the People API, for example cost or bugginess.

**Claude**

Cost isn't really the concern — the People API is free within generous default quotas (tens of thousands of read/write requests per day is typical for personal-scale use), so a few hundred contacts syncing periodically won't hit billing. The real risks are more operational:

- **OAuth token expiry, not the API itself**: `contacts` is a "sensitive" scope. If your Google OAuth client stays in Testing mode (unverified), refresh tokens expire after 7 days — a cron-driven sync would silently die weekly until you re-auth. You avoid this by setting the OAuth consent screen to "Internal" user type, which skips Google's verification requirement entirely — but only works if mylizard.net is a Google Workspace domain, not a personal Gmail. Worth confirming before committing to this approach.
- **Documented reliability gaps**: there are open/aged issue-tracker reports of contacts created via the API [not actually syncing to Google Contacts with no error returned](https://github.com/googleapis/google-api-php-client/issues/2400), `connections.list` [not returning all contacts](https://issuetracker.google.com/issues/385040567), and `updateContact`/`updateGroup` [misbehaving](https://issuetracker.google.com/issues/276340498). None of these are dealbreakers, but they mean a two-way sync job needs to verify writes landed (re-read after write) rather than trust the response, and can't be pure fire-and-forget.
- **Low investment from Google**: People API replaced the older Contacts API years ago and gets comparatively little maintenance attention — issues sit open a long time. Treat it as "good enough for a personal/internal tool," not SLA-backed infrastructure.

None of that changes my recommendation, but it does mean: build in a read-back verification step after writes, and confirm your Workspace/OAuth setup before assuming unattended long-running sync will just work.

**Claude**

Graph is very likely the easier and more reliable choice for you specifically — mainly because of how authentication works, not the API shape itself.

**The deciding factor: how the sync job authenticates**

- **Google People API**: even with "Internal" OAuth (no verification review), you still need a one-time interactive consent to mint a *refresh token*, then store and use that token indefinitely. Refresh tokens can get silently revoked (password change, security review, org policy changes, 6 months of inactivity), and when that happens your unattended cron job just starts failing until someone re-does the browser consent flow.
- **Microsoft Graph**: for a single mailbox like jr@info-assets.com, you can use **application (app-only) permissions** with the OAuth2 **client-credentials flow** — just a client ID, client secret, and tenant ID, no user sign-in, no refresh token to babysit at all. A new access token is minted fresh on every run from a static secret. The one extra one-time step is scoping it: `Contacts.ReadWrite` as an application permission is tenant-wide by default, so you'd run a single Exchange Online PowerShell command (`New-ApplicationAccessPolicy`) to restrict the app to just that one mailbox. That's a five-minute one-time setup, not an ongoing maintenance burden.

**API ergonomics**

- Graph's Contacts endpoints (`/users/{id}/contacts`) are plain REST/JSON CRUD, optional concurrency via `@odata.etag` — you can PATCH without fetching first if you don't care about clobbering concurrent edits.
- People API requires a field mask on *every* request and mandates fetching the current `etag` before any update (the write is rejected without it) — more required round-trips, more places to get it wrong.

**Maintenance**: Graph is Microsoft's flagship API surface (same one used for Outlook/Teams/SharePoint) and is under constant active development. People API is a much smaller, less-prioritized corner of Google's API surface, consistent with the reliability issues I flagged earlier.

**Bottom line**: given you're already Microsoft-centric and jr@info-assets.com is a real Microsoft-managed mailbox, I'd build against Graph with app-only credentials instead of Google People API. It sidesteps the refresh-token/verification headache entirely and the API itself is a bit more conventional to work with.

One thing to confirm: is info-assets.com's mail actually hosted on Microsoft 365 / Exchange Online (a real mailbox with a Contacts folder), or is Microsoft just handling sign-in/identity for an email hosted elsewhere? Graph Contacts needs an actual Exchange Online mailbox behind it.
