**Claude**

Yes — browser dev tools. When Fabric renders the **Manage connections and gateways** page, it has to call its own internal APIs to populate the list, and those responses include the GUIDs. You can intercept them:

1. Open **Manage connections and gateways** in Fabric
2. Open browser dev tools → **Network** tab
3. Filter by `Fetch/XHR`
4. Refresh the page
5. Look for requests to `api.fabric.microsoft.com/v1/connections` — the responses will contain the full connection objects including `id`, `displayName`, `connectionType`, and owner info

You can right-click any response → **Copy response** to grab the JSON, or copy the request as a cURL/Postman request to replay it with your own token.

This also gives you the exact endpoint and headers Fabric is using, which tells you whether there's a working non-admin connections list endpoint that just isn't publicly documented yet.

The second method — for connections already referenced in your pipelines — is just grepping the repo:

```powershell
Select-String -Path "ETL\**\pipeline-content.json" -Pattern '"connection":\s*"([^"]+)"' -AllMatches | ForEach-Object { $_.Matches } | ForEach-Object { $_.Groups[1].Value } | Sort-Object -Unique
```

That gives you every connection GUID currently wired into your pipeline files.

**You**

How does the Git integration handle subfolders?  If I put the dataflow in a subfolder, will it then go in a subfolder in Git?

---

**Claude**

Yes — Fabric Git integration maps workspace folder structure directly to the Git repo folder structure. You can see this already with your pipelines: they're in an "ETL" workspace folder, which maps to the `/ETL/` directory in the repo.

So if you put a dataflow in a workspace subfolder like `ETL/Dataflows`, it would appear in Git under `ETL/Dataflows/`. Same naming convention as pipelines — each item gets its own directory named `{ItemName}.DataflowRefresher` (or similar type suffix) containing the definition files.

One thing to be aware of: when you import the dataflow into ETL_TEST via the API, you can specify the folder path in the request body. That way it lands in the right folder from the start rather than needing to be moved in the UI afterward.

**You**

Is there a way to copy dataflows to another workspace using the API?

---

**Claude**

Not a single-call "copy" endpoint — it's the two-step process I outlined earlier:

**1. Export the definition from production:**
```
POST https://api.fabric.microsoft.com/v1/workspaces/{sourceWorkspaceId}/items/{itemId}/getDefinition
```
This is a long-running operation — it returns `202 Accepted` with a `Location` header. You poll that URL until it returns the definition payload.

**2. Create in ETL_TEST:**
```
POST https://api.fabric.microsoft.com/v1/workspaces/{targetWorkspaceId}/items
```
Body:
```json
{
  "displayName": "Your Dataflow Name",
  "type": "Dataflow",
  "folderId": "{etlFolderId}",
  "definition": { ...payload from step 1... }
}
```

To get the dataflow item IDs from production first:
```
GET https://api.fabric.microsoft.com/v1/workspaces/0cfedeac-0df9-4f18-b757-f9f73e87b66d/items?type=Dataflow
```

Would it help to build a Postman collection or PowerShell script to do this for all dataflows in one pass?

**You**

Can this dataflow stuff be done with the Power BI API, which is better documented?

---

**Claude**

No — the Power BI API only covers **Dataflow Gen1** (the original Power Query Online dataflows). Your pipelines reference `"dataflowType": "DataflowFabric"`, which means these are **Dataflow Gen2**, and those are Fabric-native items that only exist in the Fabric REST API.

The Power BI API has no awareness of Dataflow Gen2 — you'd get empty results or 404s trying to access them there.

The Fabric API is the only path for Gen2. The documentation is thinner, but the endpoints themselves are straightforward for this use case — it's really just those two calls (getDefinition + create).
