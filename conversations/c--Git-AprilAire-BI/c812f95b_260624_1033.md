**Claude**

Yes — browser dev tools. When Fabric renders the **Manage connections and gateways** page, it has to call its own internal APIs to populate the list, and those responses include the GUIDs. You can intercept them:

1. Open **Manage connections and gateways** in Fabric
2. Open browser dev tools → **Network** tab
3. Filter by `Fetch/XHR`
4. Refresh the page
5. Look for requests to `api.fabric.microsoft.com/v1/connections` — the responses will contain the full connection objects including `id`, `displayName`, `connectionType`, and owner info

You can right-click any response → **Copy response** to grab the JSON, or copy the request as a cURL/Postman request to replay it with your own token.

This also gives you the exact endpoint and headers Fabric is using, which tells you whether there's a working non-admin connections list endpoint that just isn't publicly documented yet.

The second method — for connections already referenced in your pipelines — is just grepping the repo:

```powershell
Select-String -Path "ETL\**\pipeline-content.json" -Pattern '"connection":\s*"([^"]+)"' -AllMatches | ForEach-Object { $_.Matches } | ForEach-Object { $_.Groups[1].Value } | Sort-Object -Unique
```

That gives you every connection GUID currently wired into your pipeline files.

**You**

What is "fabric-cicd"?

---

**Claude**

`fabric-cicd` is a Microsoft-backed open-source Python library that abstracts over the Fabric REST APIs to handle CI/CD deployments of Fabric workspace items. Instead of writing raw API calls, you define what you want deployed and it handles the mechanics.

In practice for your use case, an ADO Pipeline step would look roughly like:

```python
from fabric_cicd import FabricWorkspace

workspace = FabricWorkspace(
    workspace_id="prod-workspace-id",
    repository_directory="./ETL",
    item_type_in_scope=["DataPipeline", "Dataflow"]  # Lakehouse and VariableLibrary not listed
)
workspace.deploy_all_items()
```

The `item_type_in_scope` parameter is exactly what structurally prevents Lakehouses and Variable Libraries from being deployed — it's in the code, not a checkbox someone has to remember.

It became officially Microsoft-supported in February 2026, so it's no longer a community tool you'd have to worry about being abandoned.

I'm confused about the parameter.yml comment.  For some time now Semantic Models have had their own parameters which are associated with a Semantic Model/workspace combination.  When using Fabric Deployment Pipelines it allows the parameters to remain what they were in the workspace previously.

**Claude**

You've identified a genuine architectural difference, and you're right to push back.

**How Fabric Stage Promotions works for parameters:**
The model sits in the workspace and keeps its parameter values between promotions. Deployment rules apply per-stage overrides at promotion time. The workspace is the persistent home — the model and its settings live there.

**Why fabric-cicd can't do the same:**
When fabric-cicd deploys, it pushes the item definition from Git and *replaces* what's in the workspace. The definition in Git contains whatever default values were committed. If a developer saved with dev values and committed, those dev values get pushed to prod unless `parameter.yml` intercepts them first. There's no equivalent of "keep what was there before" because there's no "before" from Git's perspective — Git is always authoritative.

So `parameter.yml` isn't compensating for a lack of native parameters — it's compensating for the fact that a Git-push deployment can't preserve workspace-level state the way Stage Promotions can.

**Where this gets worse:** Direct Lake models embed `workspaceId` and `lakehouseId` directly in the TMDL definition files — those aren't native M parameters at all, so they *can't* be overridden at the workspace level. `parameter.yml` find-replace is the only mechanism available for those.

**The honest tradeoff:** For semantic models specifically, Stage Promotions handles native M parameters more elegantly than fabric-cicd does. fabric-cicd's `parameter.yml` is a workaround, not an equivalent capability.
