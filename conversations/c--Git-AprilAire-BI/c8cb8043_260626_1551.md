**On `device_profiles`** — that table came from the script's header comment, which I carried forward without questioning it. Let me explain what the script needs and you can tell me if there's a better fit in the existing model.

The script needs to know:
1. **Which App Store track IDs** go into the Mosyle "Install App" profile
2. **Which Mosyle device group** to assign the profile to
3. **A profile name** to create/find in the Mosyle UI

The original design stored all three as a flat row in `device_profiles`. But your existing model already has relevant concepts:

- `ios_apps` has `product_id` (the App Store track ID) and `package_id`
- `ios_device_apps` links apps to devices
- `customer_devices` has `app_group`, `app_catalog`, `device_profile`, and `dns_profile_name` columns

So the question is: **should the Mosyle profile be derived from the existing tables** (e.g., "give this customer's devices all apps in `ios_device_apps` for their device group") rather than maintaining a separate flat list?

If `app_group` or `app_catalog` already represents the concept of "which apps go on this device," it might make more sense to have the script query `ios_apps` filtered by that grouping — and skip the `device_profiles` table entirely.

That makes the design much cleaner. Here's what I'd recommend:

**No `device_profiles` table.** A view is the right call.

**Schema changes:**
- Add a `mosyle_install_profile_name` column to `customer_devices` — one value per device, used as the profile name in the Mosyle UI. (Could also just derive it from `device_id`, but a named column gives you flexibility to name profiles independently.)

**A view, e.g. `v_mosyle_install_profile`:**
```sql
SELECT
  cd.device_id,
  cd.mosyle_install_profile_name,
  array_agg(ia.product_id::text ORDER BY ia.name) 
    FILTER (WHERE ia.product_id IS NOT NULL) AS app_store_ids
FROM customer_devices cd
JOIN ios_device_apps ida ON ida.device_id = cd.device_id
JOIN ios_apps ia ON ia.package_id = ida.app_package_id
WHERE cd.operating_system = 'ios'
GROUP BY cd.device_id, cd.mosyle_install_profile_name;
```

**Script changes:**
- `get_profile_data()` queries this view by `mosyle_install_profile_name` instead of the `device_profiles` table
- Everything else stays the same

**No flat list benefit** in this case — `ios_device_apps` is already the source of truth for which apps belong to a device, so duplicating that into a separate table would just create drift.
