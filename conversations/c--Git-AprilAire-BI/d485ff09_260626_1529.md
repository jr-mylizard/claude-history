**Claude**

The schema is clean and already well-designed:

**`device_schedules`**: `id`, `device_id`, `name`  
**`device_schedule_blocks`**: `id`, `schedule_id`, `day_of_week` (0–6), `start_time` (time), `end_time` (time)

This is the right normalized structure for recurring weekly schedules. The write-back complexity you mentioned isn't a schema problem — it was a WeWeb problem. WeWeb's calendar emits ISO datetimes on interaction, so saving changes meant converting those back to `day_of_week + time`, which required the view-to-function roundtrip.

In Next.js with FullCalendar React we don't have that constraint. The approach that avoids all that complexity:

- **Calendar = display only** — reads from `vw_device_calendar` (or we generate events client-side from the blocks), no write-back through the calendar at all
- **Schedule editing = dedicated form** — directly reads/writes `device_schedules` and `device_schedule_blocks`, completely bypassing the calendar for mutations

This matches what you confirmed about the Schedules datagrid being read-only with a separate edit form. The schema stays as-is — no redesign needed.

**Claude**

The view is sophisticated but correct — it handles the current week, timezone, overnight splits, and color assignment from `format_colors`. No redesign needed. Here's the complete picture:

**The view generates read-only calendar events for the current week.** It uses `date_trunc('week', now() AT TIME ZONE timezone)` so it always anchors to today's week. The `id` it returns is a synthetic `row_number()` — not a stable DB key.

**This is why write-back was complex in WeWeb**: the calendar IDs aren't real, drag-drop gives you ISO datetimes, and you'd have to reverse-engineer which `device_schedule_blocks` row it corresponds to.

**In Next.js, the fix is simple:**
- Calendar stays **display-only** (`disableInteractions: true` equivalent in FullCalendar React)
- All schedule CRUD (add/edit/delete blocks) goes through a form that writes directly to `device_schedules` + `device_schedule_blocks`
- After a save, just re-query the view to refresh the calendar

No schema changes, no write-through-view complexity, the view stays exactly as-is.
