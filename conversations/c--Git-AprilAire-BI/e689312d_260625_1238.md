---

**Distinguishing Mac script vs manual iOS enrollment**

The Mac script (`enroll-iphone.sh`) opens a URL — and looking at the WeWeb page, it already passes `?imei=XXXXXX` as a query param to pre-fill the IMEI field. So the simplest approach is to have the Mac script also append `?source=mac`, and the page conditionally shows/hides the app list section based on that. No backend change needed, just a query param check in the React component.

---

**Handling screenshots — steps and effort**

**Option A — Email to you (minimal effort, ~0 dev work)**
Just remove the app list field entirely from the iOS form and add a line: "Email your app list screenshots to jr@mylizard.net." You handle it manually. No parsing, no infra.

**Option B — Upload screenshots, Claude parses them (~medium, 2–4 hours)**
1. Change the file input to accept `image/*` (multiple files)
2. Add a Next.js server action that takes the uploaded images, sends them to Claude API (vision), and returns a structured app list
3. Display the parsed result to the user for confirmation before submitting
4. Pass the parsed list to the edge function

The main complexity is the Claude API call (straightforward with vision) and deciding what structured format the edge function expects. The `pre-enrollment-ios.ts` in `Test_Unified` likely has a specific format for the app list — worth checking before building this.

**Option C — Upload screenshots, process async (~higher, separate edge function)**
Upload images to storage → edge function parses them with Claude → webhook or polling updates the device record. More robust but significantly more moving parts.

---

My take: **Option A** is the right default until you have enough iOS device (non-Mac) enrollments to justify the automation. **Option B** is worth doing once the Unified branch is merged and you can see exactly what format `pre-enrollment-ios.ts` expects for the app list. The query param approach for Mac vs manual works regardless of which option you pick.

---

**You**

Why is option C harder than option B?  Is it because you want to display them to the user?

---

**Claude**

Yes, exactly. If you don't show the parsed result to the user, B and C collapse into roughly the same thing — upload images, call Claude, pass the result to the edge function. The async architecture in C (polling/webhooks to notify when parsing is done) is only necessary if the parsing takes long enough that you can't just await it inline.

In practice, Claude parses a few screenshots in 2–3 seconds, so you can do it synchronously in a server action with no async coordination needed. The confirmation display in B is optional — you could just parse silently and submit in one shot.

So the real spectrum is simpler than I made it:

- **No automation**: remove the field, email you the screenshots
- **Silent parse + submit**: upload images → server action calls Claude → result goes straight to edge function, user just sees "submitted"
- **Parse + confirm**: same but show the parsed app list so the user can spot-check before submitting

The confirm step adds maybe an hour of UI work but gives you a quality check during enrollment. Probably worth it given that a bad app list is hard to debug later.
