## What Fabric Native Git Integration Actually Solves (vs. Doesn't)

**The good news**: When you connect a workspace to Git through Fabric's native Git integration (not manual export), Fabric replaces same-workspace item GUIDs with *logical item references* on export. This means `dataflowId`, `pipelineId`, `sqlEndpointId`, and `datasetId` pointing to items in the same workspace get resolved automatically on sync-in to a different workspace — you don't need to parameterize those.

**What it does NOT solve**:
1. **Lakehouse references in mashup.pq** — the `workspaceId` and `lakehouseId` in the Power Query destination queries are treated as opaque literals. Fabric doesn't rewrite these on import.
2. **DB2 source connection** — the IP/database in `DB2.Database(...)` is a connection string, not an item reference.
3. **`connection` GUIDs** in `externalReferences` — these are gateway connection IDs, workspace-specific, and need a matching named connection in the target workspace.

## Lakehouse Git Integration + Schema Changes

When a Lakehouse is in Git, Fabric stores only the **schema definition** (table names, column definitions) — no data. When you sync to a new workspace, it creates an empty Lakehouse with the same schema.

For schema changes with existing data:
- **Add column**: Delta Lake handles this with schema evolution — existing rows get `null`. Safe.
- **Rename column**: Not supported in-place by Delta. You'd add the new column, backfill, drop the old. Requires care.
- **Change type**: Generally requires table recreation — destructive.
- **Drop column**: Delta marks it as phantom; physically removing requires enabling the Drop Column writer feature (Delta protocol version 7). Don't do this casually in production.

So additive schema changes flow cleanly through Git. Destructive ones need a migration plan.

## Destructive Schema Changes: What Fabric Actually Does

Fabric applies the change and **does not warn you or ask you to do it yourself**. The behavior breaks down by change type:

**DROP TABLE**: Fabric executes the DROP against the Delta table in the target workspace. If that table has data, the data is gone. No confirmation prompt, no pre-flight check.

**DROP COLUMN**: This depends on Delta protocol. Fabric needs Delta writer version 7 (the "Drop Column" feature) enabled on the table. If it's not enabled, the sync **fails with an error** — the deployment does not succeed and the column isn't removed. If it is enabled, the column is logically dropped (Delta marks it in the transaction log; underlying Parquet files aren't rewritten, but the column is inaccessible going forward).

**ALTER COLUMN TYPE**: Delta Lake doesn't support this natively. Fabric typically handles this by dropping and recreating the table, which **destroys all data in that table in the target workspace**. This is the most dangerous case.

**The short version**: Fabric does not protect you. It tries to apply the schema change. It either succeeds (with potential data loss) or fails with an error if the underlying Delta feature isn't present. There is no "mark it successful and ask you to do it" mode — that would be a Fabric Deployment Pipeline rule, but even those don't intercept schema DDL.

**Practical implication**: For your Dev → Test flow, destructive schema changes should be accompanied by a migration script (a Notebook that applies the Delta change in a controlled way) that you run *before* the Git sync, so the target schema already matches what Git expects. Otherwise you risk a broken sync or silent data loss.

## Should Lakehouses Be Separate from Git-Connected Workspaces?

**Yes, this is the right call — and it's the standard enterprise pattern in Fabric.** Here's the reasoning:

- Lakehouses are fundamentally a **data platform** concern, not a code deployment concern. The schema lives there, but so does the data — and data doesn't deploy; it accumulates.
- Schema changes to a Lakehouse are better managed as **numbered migration scripts** (Notebooks) run as part of a deployment process, not as Git sync operations. Think Flyway/Liquibase but as Fabric Notebooks.
- Git-connected workspaces should contain things that are purely code artifacts: Pipelines, Dataflows, Warehouses (views only), Notebooks, Semantic Models, Reports.

The practical pattern: one **Platform** workspace (or Dev/Prod Platform workspaces if you need data isolation) holds the Lakehouse(s), with no Git integration. Everything that processes or presents data is in Git-connected workspaces.

For schema migration specifically, **Flyway and Liquibase both support JDBC**, and Fabric's Lakehouse SQL Endpoint exposes a JDBC-compatible SQL endpoint — so you could technically use either. But in practice, most teams use a numbered Notebook approach since you're already in Fabric and Notebooks run natively against the Lakehouse.

**You**

What is the difference between a read-navigation binding target and a write sink?

---

**Claude**

In Power Query / Dataflow Gen2, `Lakehouse.Contents()` can be used in two different roles:

**`_DataDestination` queries (write sinks)** — The query engine evaluates the full `Lakehouse.Contents()` navigation chain to get a table reference, and then Fabric's write engine pushes data *into* that reference. Because the Lakehouse connector is being treated as a writable target, the query optimizer may try to "fold" the write operation back down into the Lakehouse connector itself — essentially asking the connector to handle the write natively. That fold attempt conflicts with Delta Lake's versioning system, producing the "value does not support versioning" error. `EnableFolding = false` shuts that off and forces the write to go through the standard non-folded path.

**`DefaultDestination` (read-navigation binding)** — This is just a navigation path expression. Queries marked `BindToDefaultDestination = true` don't evaluate `DefaultDestination` as a write target themselves — instead, the Fabric runtime reads the path it points to (the schema level in the Lakehouse), appends the query's own name as the table name, and handles the actual write internally. The Power Query fold optimizer isn't involved in the same way, so the versioning conflict doesn't arise.

The practical distinction: `_DataDestination` queries go through the standard Power Query evaluation pipeline where folding can be attempted. `DefaultDestination` is resolved by the Fabric runtime outside that pipeline. That's why the latter didn't need `EnableFolding = false` and the former did.

**You**

Why are there two kinds of destinations?  Does it make sense to standardize on one?

---

**Claude**

**Why two exist:** They evolved organically from how the Fabric UI generates code.

- When you set up a destination via UI with automatic schema inference and no column remapping, Fabric writes `BindToDefaultDestination = true` on the source query and creates one shared `DefaultDestination` navigation target.
- When you configure explicit column mappings (`Kind = "Manual"`) or the table name needs to differ from the query name, Fabric generates a separate `_DataDestination` query per table instead.

So the mix in these dataflows reflects which tables were configured simply vs. which got manual column mapping at setup time — not a deliberate architectural choice.

**Should you standardize?**

The constraint is that `DefaultDestination` is singular — one per dataflow, shared by all bound queries. Since all your tables in a given dataflow land in the same schema (controlled by the Variable Library), that constraint isn't a problem here.

However, looking at the existing code, the "Manual" destinations have explicit `ColumnSettings` with column-to-column mappings. Those were auto-generated by Fabric when you configured the destination against a table that already existed (in dbo). Now that `IsNewTarget = true` is set everywhere, those column mappings are mostly inert — the table gets created fresh each run anyway.

**Practical answer:** For the current dataflows, it's not worth the churn to standardize. The `_DataDestination` pattern with `EnableFolding = false` is working and explicit. For any *new* dataflows you build, defaulting to the `_DataDestination` explicit pattern (without relying on the UI's auto-generated column mappings) would be the more consistent choice and avoids the DefaultDestination's limitation of being a single shared target.

**You**

How does the script work?

---

**Claude**

The script has two independent processors — one for `mashup.pq`, one for `queryMetadata.json` — run against every `.Dataflow` folder it finds.

**mashup.pq processor**

First it splits the file at `section Section1;`, separating the document-level header from the query blocks. It scans the header for a `StagingDefinition` line to preserve, and discards everything else (including any old `DefaultOutputDestinationSettings`).

Then it parses the query blocks using one rule: any line starting at column zero is either an attribute (`[...]`) or the start of a new query (`shared ...`); anything indented is a continuation of the current query. This gives it a list of `(attribute, query_lines)` pairs.

It then walks those pairs and makes three decisions per block:

- Name ends with `_DataDestination` → delete it
- Name is `DefaultDestination` → replace with the canonical single-line form
- Name is a variable or `DefaultStaging` → keep unchanged
- Anything else → it's a source query; replace its attribute with `BindToDefaultDestination = true`, preserving the `Description` value if one exists

Finally it reassembles the file: `StagingDefinition` header (if any), then the new `DefaultOutputDestinationSettings` header, then `section Section1;`, then the transformed query blocks.

**queryMetadata.json processor**

Simpler — it loads the JSON, rebuilds the `queriesMetadata` object with `DefaultDestination` first (generating a new GUID if it wasn't already there), then copies every existing entry that doesn't end with `_DataDestination`. The `connections` array is left untouched.

**What it doesn't touch**

The source query bodies themselves — the DB2 navigation steps, any transforms, the `let...in` structure — are passed through verbatim. The script only changes attributes and destination infrastructure, never the data logic.
